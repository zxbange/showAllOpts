# 博主动态监控

页面入口：侧边栏或首页的「博主动态监控」，路径 `/social-monitor`。

雪球采集使用当前网页的 `https://www.xueqiu.com/statuses/original/timeline.json`，每页 10 条，读取响应 `list` 中的原创时间线内容。兼容旧 `statuses` 结构；不再请求旧 `/v4/statuses/user_timeline.json`。该来源的转发覆盖尚未验证，不能保证包含所有转发。页面返回的 `description` 用作正文、`title` 用作标题、`created_at` 用作发布时间；未返回平台昵称时继续使用已有名字或备注。修改接口后需重启后台，原有平台暂停需人工确认恢复；不需重新填写仍有效的 Cookie。
页面直接打开，不需要账号密码；原监控管理接口不要求身份验证。任何能访问网站的人都可以管理博主、修改通知与平台凭据配置、启停监控。敏感配置仍加密保存，接口不会返回明文密钥或 Cookie。新增的 `/api/v1/social-monitor/browser/*` 服务器浏览器接口单独要求管理密钥，配置与使用见 [服务器扫码登录](social-browser-login.md)。

## 使用

若普通 HTTP 诊断返回 `unidentified_html`，可在同一服务器做一次 Chromium 对照：

```bash
sudo -u ubuntu env APP_ENV_FILE=config/app.config backend/.venv/bin/python scripts/check_xueqiu_browser.py
```

该工具把已保存的 Cookie 导入临时浏览器目录，打开相同帖子接口并短暂等待页面渲染；不读写已有浏览器资料、不更新数据库或 Cookie，也不恢复监控。与普通 HTTP 诊断不同，一次浏览器页面加载会产生正常的资源请求和跳转；工具限制访问域名、总请求数与导航次数，不解决验证码、不反复刷新。输出仍仅包含分类及非敏感状态。`posts_json` 表示浏览器方式本次成功，可进一步评估抓取客户端适配；`security_block_page`、`verification_page`、`login_page` 表示浏览器也收到相应限制，不能据此认定具体封禁对象；`unidentified_html` 表示仍无法确认，需要进一步检查接口适配。浏览器启动要求与扫码登录一致，包括安装 Chromium 和可用的沙箱。

雪球携带 Cookie 后仍返回网页时，可在服务器项目根目录运行一次只读诊断：

```bash
sudo -u ubuntu env APP_ENV_FILE=config/app.config backend/.venv/bin/python scripts/check_xueqiu_response.py
```

按实际服务账号和配置路径替换 `ubuntu`、`config/app.config`。脚本读取已有加密 Cookie，优先选择启用的一个雪球博主，只请求一页，不重试、不跟随跳转、不恢复监控，也不修改数据或凭据。输出仅包含 HTTP 状态、响应类型与分类，不输出 Cookie、帖子、网页正文或原始跳转 URL。`security_block_page` 表示网页有明确拦截提示，`login_page` 表示有登录提示，`verification_page` 表示要求人工验证，`unidentified_html` 表示证据不足，`api_host_redirect` 提示需检查域名适配，`posts_json` 表示本次正常返回帖子列表；分类仅描述本次响应，不能单独确定 IP 或账号被封。响应最多读取 512 KiB，超限会标记 `body_truncated`，此时结构判断可能不完整。

1. 打开页面后默认显示「最新动态」。进入「通知设置」，填写机器人密钥（Telegram Bot Token）、接收会话编号（Chat ID）并保存，点击发送测试消息验证。
2. 在同一分区使用「扫码登录」：输入服务器私有配置的管理密钥，打开对应平台登录窗口，在手机确认后自动保存 Cookie。也可继续手动填写 Cookie：从自己已登录的平台浏览器开发者工具 Network 请求头中复制，微博使用 `m.weibo.cn` 登录态，雪球使用 `xueqiu.com` 登录态。保存后不返回明文，输入框留空保留原配置。
3. 切换「监控博主」添加用户：选择平台，填写数字 UID 或包含 UID 的主页链接，可填写备注。已预填微博主页 `https://weibo.com/u/3962719063`，点击添加即可。
4. 点击「启动监控」。后台每轮完成后重新随机等待 **10～16 分钟**，页面显示最近和下次检查时间。按北京时间 **00:00（含）～07:00（不含）不请求微博/雪球，也不推送帖子**。07:00 恢复抓取，补抓夜间新帖并推送；服务须保持运行，停机时在启动后的允许时段补抓。关闭网页不影响后台。
5. 普通首次采集最多读取 3 页历史记录，仅展示、不推送。从之后发现的新帖子开始推送；若用户在夜间已添加并启用，次日首次采集也会推送对应夜间的新帖。页面显示发布时间、正文、原文链接、推送状态及异常。页面每 10 秒刷新展示数据，不额外触发平台抓取。

改用扫码登录无需先清空手动 Cookie，验证成功后会自动覆盖对应平台的凭据。需要移除时，在「通知设置 → 通知配置与手动凭据」点击「清空已保存的微博/雪球登录凭据」。留空后保存配置仍然表示保留原值。清空操作只移除监控使用的对应 Cookie，不影响另一个平台、Telegram 配置、博主或帖子，也不会删除服务器浏览器资料目录或注销平台账号；建议先暂停对应平台的博主，重新登录成功后再恢复。

支持按平台/用户筛选和分页；支持暂停、恢复用户以及暂停所有监控。删除用户同时删除其本地帖子记录。恢复时会检查最近可见帖子；暂停期间超过抓取窗口的内容可能遗漏。

「最新动态」支持关键词检索：输入关键词后点击「搜索」或按回车，在全部已保存帖子的正文中匹配，可叠加平台、用户筛选，并按匹配结果分页；点击「清除搜索」恢复列表。搜索不会请求微博/雪球。关键词按字面匹配，不把 `%`、`_` 作为通配符，英文字母不区分大小写。

用户卡片、筛选列表和动态作者优先显示平台博主名字，其次显示备注；尚未获取名字且未填备注时显示「待获取博主名称」，不展示 UID。已有帖子中保存的名字会自动回填，后续正常抓取时也会刷新博主名字，不增加额外平台请求。UID 仍保存在服务端，用于定位和去重。

## 持久化及后台任务

- 在 `${LOG_DIR}/social/monitor.sqlite3` 保存用户、帖子、配置、发送进度和检查时间；不依赖市场数据 MySQL，也不要求修改源库权限。
- 帖子默认保留最近一年：后台按北京时间每天首次运行时检查，删除去年同日零点之前发布的帖子（含待推送记录）；闰年 2 月 29 日的去年日期按 2 月 28 日计算。不能解析发布时间时，按采集时间判断。监控暂停时仍清理，停机后启动会补做当天检查。清理日期和删除数量保存在 `config` 表中，重启不重复清理；过期旧帖再次出现在抓取结果中时会被过滤。博主、Cookie、Telegram 配置不受影响。SQLite 删除后释放的页供后续数据复用，数据库文件不保证立即缩小。
- Token、Chat ID 和 Cookie 使用 Fernet 加密后落盘，密钥位于同目录 `secrets.key`。备份/迁移时应同时保留数据库和密钥，限制整个目录的访问权限。丢失密钥后无法解密已有配置。
- 多 Uvicorn worker 通过同一目录下的文件锁只选一个后台执行者；实例必须共享此目录，独立目录或不同服务器不会互相去重。`SOCIAL_WORKER_ENABLED=false` 仅关闭当前进程的后台执行，接口仍可用于管理。
- 每个博主保存成功检查水位和未完成分页位置。日常从第一页开始，碰到上次成功检查以前已记录的非置顶帖子后停止翻页；已记录的帖子不再请求微博长文。大量夜间新帖按页入库，每轮最多 20 页，未完成的补抓在后续轮次继续，同时重新检查第一页。平台请求之间短暂随机等待，避免集中请求。
- HTTP 429 时读取 `Retry-After`，无有效等待时间时默认退避 30 分钟；普通网络/服务器错误采用逐步延长的退避，最多 6 小时。不会在每轮仍频繁请求受限平台。
- 出现验证码、登录失效、HTTP 401/403/418、登录验证跳转或接口返回验证网页时，**暂停整个对应平台**，其他平台可继续。暂停原因、事故编号和通知状态保存在 `config.platforms` 中；重启、到 07:00、修改 Cookie 或切换总开关都不会擅自恢复。
- 自动暂停会在页面直接展示原因、可用的 HTTP 状态码和暂停时间，区分验证码、登录失效、访问拒绝及登录/验证跳转；退避等待显示网络连接失败、超时或限流原因和最早重试时间。每个博主卡片同步显示当前暂停或暂缓原因，手动关闭和夜间休息也有对应说明。诊断仅展示经过分类的安全信息，不回显平台响应中的 Cookie、密钥或完整原始错误。
- 每次自动暂停发送一条 Telegram 人工处理提醒；成功后不重复，失败则持久保留并按 3～6 分钟随机间隔重试。管理提醒可以在夜间发送。处理完浏览器登录/验证码并更新 Cookie 后，点击页面的「人工处理完成，恢复微博/雪球」恢复；恢复时仍遵守夜间休眠。
- Telegram 帖子发送失败保留状态，下轮重试。长消息按 UTF-16 长度分段，并持久化每段发送进度。Telegram 成功后、本地落盘前发生故障仍可能产生重复帖子或提醒，无法保证跨网络的严格仅一次。
- 为避免泄露 Telegram Token，HTTPX / HTTPCore 请求 URL 日志被设为 WARNING。

## 抓取范围与访问限制

使用微博和雪球网页内部接口，不是全量历史归档；补抓依赖平台仍然返回历史帖子，删除、不可见、平台排序/接口变化或一年保留限制可能导致内容无法补齐。按帖子 ID 去重，编辑旧帖不会再次推送。降低频率和自动暂停不能保证平台不会限制账号/IP。
微博长文额外读取全文，转发附接口提供的原文。推送文字及原文链接；图片、视频通过原文查看。可识别的发布时间统一为北京时间，不能解析时保留接口原值。

平台接口可能变更或要求登录/人工验证，届时需要更新 Cookie 或调整解析。程序不绕过验证码或权限限制。目前未使用真实 Cookie 和 Telegram 凭据完成端到端联调。

## Linux 更新与配置迁移

1. 拉取代码并执行现有部署流程：在项目根目录运行 `bash deploy.sh`。它会安装锁定依赖、构建前端、重启 `showallopts-api` 并发布静态资源。本模块需要的 `httpx`、`cryptography`、`portalocker` 已在依赖锁定文件中。
2. 在服务实际选中的私有配置（通常为 `config/app.config`）确保 `SOCIAL_WORKER_ENABLED=true`。无需配置管理员账号密码，旧的 `SOCIAL_ADMIN_USERNAME`、`SOCIAL_ADMIN_PASSWORD`、`SOCIAL_ADMIN_PASSWORD_HASH` 已不使用，可删除。不要覆盖现有数据库配置；修改私有配置后重启服务。网站若已有 Nginx 等部署层认证，此修改不会调整部署层认证。
3. 不迁移本地状态时，在 Linux 页面重新添加博主、填写机器人密钥、接收会话编号、微博/雪球登录凭据，然后启动监控。Git 不携带这些私有数据。
4. 要保留博主、帖子、去重进度和推送配置，先停止源端与目标端后端，再通过私有渠道复制完整的 `${LOG_DIR}/social/`，至少包含 `monitor.sqlite3` 和与之配对的 `secrets.key`，放到目标配置对应的同一路径下。密钥和数据库不可分开替换。已有 Linux 数据需要先备份，不要盲目覆盖。
5. 确保目录和文件由实际 systemd 服务账号拥有：目录建议权限 `700`，数据库和密钥 `600`。仓库 service 示例账号为 `showallopts`；现有机器如果使用覆盖配置运行于 `ubuntu`，以 `systemctl show showallopts-api -p User -p Group` 的结果为准。`LOG_DIR` 必须位于服务的 `ReadWritePaths` 许可范围，默认 `log/` 已在许可范围内。
6. 状态库迁移后保留启停与自动暂停状态；普通登录凭据可按需重新配置，平台可能因服务器 IP/登录态变化要求重新登录。检查页面提示，完成验证后再人工恢复。北京时间时段由代码指定，无需把 Linux 系统时区改为北京时间。

更新不会修改市场数据 MySQL 结构；监控 SQLite 的新增字段由后端启动自动升级。不要同时运行使用同一账号但不同状态库的 Windows/Linux 监控实例，以免重复请求和推送。
