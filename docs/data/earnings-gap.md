# 净利润断层观察名单

> 默认启用本地缓存：采集入库后，等待配置的每日自动同步，或在网页“数据同步”中手动同步。页面刷新读取当前快照，详见[本地缓存说明](../operations/local-cache.md)。


> 独立与批量入口默认按上次成功检查日期增量筛选（`skip_existing=True`），同季度已入库股票保留原始快照。已入选股票的收盘表现单独每日更新，同股票多季度共用一次行情查询，同日已完成的跟踪跳过。只有显式调用独立脚本的 `run(skip_existing=False)` 才会整批替换当前目标季度。详见 [批量采集说明](collector-batch.md)。

## 使用方式

1. 将 `collectors/净利润断层_数据库版.py` 上传到聚宽研究环境。同时上传 `mysql_connector.py`，在其中填写与项目相同的 MySQL 数据库连接信息。
2. 直接粘贴运行，或在 Notebook 中执行：

   ```python
   %run -i 净利润断层_数据库版.py
   ```

3. 采集账号需要建表、查询、插入、删除权限；网页账号只需 SELECT。脚本使用 `earnings_gap_run`、`earnings_gap_stock` 和季度版本表 `earnings_sync_head`；新版增加 `earnings_sync_migration` 迁移标记表。四表必须为 InnoDB，脚本不会自动转换已有表引擎。
4. 运行成功后，打开“发奋墙 → 净利润断层”。列表支持搜索、财季、行业、公告类型和排序；在固定高度区域使用滚轮查看，表头固定，不显示翻页按钮。点击股票查看三类公告原始数据以及信号前 10、后最多 20 个交易日日线。
5. 每次需要更新时在聚宽重新运行。网页不会自动执行聚宽，也不包含下单逻辑。

### 收盘表现与全部历史保留

- 列表和详情新增“断层日涨幅”和“距今涨幅”。断层日涨幅为 `(断层日收盘 / 前收盘 - 1) × 100%`，旧记录可由高开幅度和收盘相对开盘涨幅还原。
- 距今涨幅为 `(最新收盘 / 断层日收盘 - 1) × 100%`。两个价格来自同一次前复权行情查询，避免除权、分红导致不同复权基准混用。16:00 前不使用当日未完成收盘，周末用最近交易日；停牌使用最后一个实际交易日并显示日期。
- 新增小表 `earnings_gap_performance` 保存跟踪结果，由采集脚本计算写入，网页同步该表并读取展示。无需修改旧表字段，也不重复传输原有公告和 K 线 JSON。源库尚未升级时仍可浏览原数据，距今涨幅显示待采集。
- 升级实际使用的独立或批量聚宽脚本，运行一次，再同步净利润断层模块，才能看到最新距今涨幅。首次跟踪会补取全部已入选股票的行情。历史全市场重建由下述 history_mode 单独执行。
- 独立和批量脚本均不再按五年删除历史报告期。股票快照、季度头、版本和迁移标记持续保留；仅清理显式重建后已不再存在的股票跟踪记录。旧版脚本已经删除的数据无法凭空还原，需重新执行历史恢复。后端按源库现存季度和版本同步，不另设五年过滤。
- 页面按“报告季度”过滤。一只股票在已采集并保留的多个季度入选，会标注入选季数和具体季度；详情中的季度可点击切换。不把未采集季度视为已检查。

仓库中的采集脚本只包含脱敏配置。本地 `original` 私有副本与网页的 `config/app.config` / `backend/.env` 均不应上传真实凭据。

## 筛选口径

- **统一报告季度**：运行所在季度之前的最近一个完整季度。例如 2026-10-17 取 2026-09-30；2027-01-01 取 2026-12-31。季度末当天仍取上一季度，下一季度开始自动切换。不自动混入上一期财报。
- **范围**：聚宽 `get_all_securities(types=['stock'])` 提供的全部 A 股，不限 3/5 只，不使用原策略的行业白名单、私人黑名单和持仓限制，也不额外排除 ST。覆盖范围受聚宽数据权限和股票支持范围约束。
- **三条财务路径取并集**：快报归母净利润为正且同比 ≥ 20%；预告增幅下限 ≥ 20%（沿用原程序，不增加盈利为正限制）；正式财报归母净利润为正且同比 ≥ 20%。
- 只读取目标报告期并且截止日期前已披露的记录。目标期的快报、预告可以早于季度结束发布，也会检查其对应行情。
- **价格条件**：公告对应交易日的开盘价 > 前一交易日收盘价 × 1.03，且收盘价 ≥ 开盘价。等于 3% 不算。当天停牌、无成交，或者没有可验证前收盘价时不产生信号。
- **公告日期映射**：交易日公告使用当日日线，沿用用户确认的原程序口径；非交易日公告顺延到下一个交易日，绝不使用公告前的价格。不会跳过停牌一直寻找未来的上涨日。
- **不是严格缺口策略**：不要求当日最低价高于前日最高价，也不检查 5 日不回补。
- **不是公告因果验证或回测**：日期级数据无法区分盘前/盘后披露。股价和利润同时符合条件，不代表公告导致上涨，不代表超出分析师预期。复权行情和源表更正可能使重采结果变化。
- 一只股票可有多个命中事件。列表以最新信号日期为主，同日按高开幅度、来源编码确定稳定顺序；详情保留该股票该期取得的全部公告和命中标记。不会用最新不合格公告替换历史命中事件。
- 正式财报查询通过 `get_fundamentals(date=截止日)`，并限定利润表与指标表同一报告期；两个发布日期不一致时，以较晚日期关联行情。该接口返回截止日可见的财报版本，不提供完整的财报修订历史。快报和预告使用主键分页，避免行数上限截断。

## 数据口径

| 字段 | 单位 / 含义 |
| --- | --- |
| 总市值、流通市值 | 亿元，截止交易日的估值快照 |
| PE（TTM）、PB | 倍，保留负数；缺失显示 —，不补零 |
| 归母净利润 | 标准化金额为元；正式财报沿用原策略单季度字段，快报使用源表报告期金额 |
| 利润同比 | 百分数，25 表示 25%；预告列表展示区间下限 |
| 高开幅度 | 相对前一交易日收盘价 |
| 当日变动 | 收盘相对开盘价 |
| 断层日涨幅 | 断层日收盘相对前收盘；不等同于收盘相对开盘 |
| 距今涨幅 | 最新已采集收盘相对断层日收盘，同基准前复权，展示实际价格日期 |
| 细分行业 | 截止日优先申万三级，缺失依次回退二级、一级，并标注实际层级 |
| 公告原始数据 | 保存源表字段、报告期、发布日期、来源类型；未标准化的预告金额字段保留原值，不猜测单位 |

快报/预告与正式财报的数据口径不同：前两者通常为报告期累计，正式财报的 `income` / `indicator` 沿用单季度接口。页面分别标注，不能把三季报累计同比与第三季度单季同比直接当作同一指标比较。归母净利润及增幅以触发信号的来源为准。

自动“断层原因分析”已移除，列表和详情只展示财务、行情及公告证据。为兼容已建表，保留旧的非空 `analysis` / `analysis_basis` 列，新脚本以空字符串占位；后端不会读取或返回这两个字段。无需删表或迁移已有数据。更新网页即可隐藏旧分析；同步更新聚宽脚本可停止生成新分析。公告自带的原因原文仍属于原始数据，继续保留。

- 默认结束日期为北京时间当天；16:00 前只处理此前的完整交易日，周末使用最近交易日。建议收盘数据发布后运行。
- 日常读取 `earnings_gap_run.as_of_date` 作为成功检查截止日，只查询该日至本次完整收盘日之间的披露（包含起点一天）。三类公告均在源查询中限制日期；周末披露会随下次交易日检查。换季接续上次成功日期，仍只筛选当前目标季度。
- 零命中也更新检查日期，并与新入选快照在同一事务提交。查询、筛选或写入失败不推进日期；同一截止日重复运行跳过公告筛选。沿用已有季度元数据，无需新增表或清空数据。空库首次只检查最新完整收盘日；历史补采使用下文的 `history_mode`。
- 日常不复查窗口以前的公告及修订；源平台后来补录但披露日期早于窗口的数据，需要显式历史补采。历史模式不受日常检查日期限制。
- 仅财务条件通过的候选股票读取行情，每批最多 50 只，共用一次交易日历；取价截至相关公告对应交易日后最多 20 个交易日，满足信号和详情图所需。进度分别显示披露窗口、财报批次、行情批次及已入选股票收盘跟踪。
- 入选快照、孤立跟踪清理和每日收盘跟踪分阶段提交；跟踪失败保留原跟踪数据，不撤销已经成功的新增快照。显式整批模式只替换目标季度快照，所有其他季度保留。合法“零命中”会保存零数量，不冒充尚未采集。
- 这是季度观察名单，默认重采保留首次入库的股票快照并新增新股票；显式整批模式才替换目标季度结果，不是每天的历史名单存档。列表默认请求当前目标季度，没有数据时不自动回退旧季度。
- 列表接口在数据库分页，最多 100 条/次；前端自动取齐所选条件的记录后滚动展示。若后续批次失败或名单发生变化，明确报错并允许重试，不把部分记录当作完整结果。不读取公告及日线 JSON 大字段；详情按季度和代码复合主键读取。

## MySQL 小数精度警告

出现 `1265 Data truncated for column 'open_gap_pct' / 'intraday_pct'` 时，常见原因是涨幅计算结果的小数位超过表中 `DECIMAL(20,6)` 的 6 位精度。MySQL 对超出的小数位进行舍入并产生提示，不表示整个字段被清空；应结合日志确认事务是否已提交。

采集器在写入前按每个 Numeric 字段的声明使用 Decimal 和 ROUND_HALF_UP 量化：比例、市值及估值保留 6 位小数，归母净利润金额保留 4 位。直接将 Decimal 交给驱动，避免转回 float 引入长尾；同时拒绝非有限值和超出字段范围的值。原始价格筛选先于量化，严格大于 3% 的条件不变。极接近阈值的命中值可能显示为 3.000000%，详情中的原始公告信号仍保留计算值。

上传更新后的私有采集脚本到聚宽重新运行，即可刷新当前季度结果；不需要删表、清空历史或修改网页。脚本不会屏蔽数据库警告，也不关闭严格模式。如果更新后仍有相同警告，请核对实际表的 DECIMAL 精度是否与脚本定义一致，`create_all` 不会修改已有列。

参考：[MySQL 定点数舍入说明](https://dev.mysql.com/doc/refman/8.0/en/precision-math-expressions.html)。

## 数量与版本一致性升级

用户需同时替换实际使用的独立/批量聚宽脚本，停止旧副本继续向同一表写入，并在聚宽按原方式运行一次；仅部署网页后端不能修改源库版本。新脚本成功处理当前季度后，自动检查所有历史季度的一次性迁移标记，不需要重查历史聚宽行情。

- 默认新增模式发现声明数量小于已有实际股票数量时，校验完整记录后在同一事务修正数量并更换 generation；正常新增仅递增 revision。声明数量大于实际数量或只有股票而缺季度元数据时拒绝“调低计数修复”，避免把丢失/半成品当作完整结果。
- 对未迁移季度，按版本行加锁，检查季度元数据、实际数量、必要字段和日期/数值约束；通过后更新 generation/revision，并在同一事务写入 `earnings_sync_migration(protocol=2)`。迁移不删除或覆盖股票及JSON数据。即使原数据的数量此前已修正、旧版本没有变化，也会建立一次新基线，覆盖历史季度。
- 初始化只建兼容表并检查结构，不给未经校验的历史数据生成有效版本。迁移标记与版本一起提交或回滚；重复运行、新进程重跑均跳过已迁移季度。并发采集器必须均使用新协议和InnoDB事务，版本行锁负责串行化发布。
- 迁移按季度提交。若某个旧季度校验失败，该季度不发布新版本，错误包含季度和数量；已校验并提交的季度无需重复迁移。当前季度的正常采集事务可能已成功，不能将迁移失败理解为所有已完成工作都回滚。修复真实缺失数据需要针对该季度核查/重采，程序不会自动删表或清空缓存。
- 网站同步在同一源事务内校验各季度声明数量与实际数量，即使请求完整同步也不能绕过不一致。版本未推进等错误包含季度、源/缓存数量和版本，失败继续保留上次成功快照。

一次性成本：源库对每个未迁移季度做数量和约束检查、写一个迁移标记及新版本；网站下次同步仅对 generation 改变的季度重新读取现有快照（包括其JSON字段）。之后恢复日常新增传输；每次同步增加一次按季度聚合的数量校验，不重复下载未变化季度的股票明细。校验依据已保存元数据与记录，不宣称能重新证明聚宽上游是否漏采了其本身未声明的数据。

本次开发测试使用离线SQLite和模拟接口，未操作生产数据库、缓存或聚宽任务。真实MySQL并发与具体数据规模的耗时需部署使用后观察。

### 引擎检查失败的诊断

采集器在同一连接上确认已选择数据库，再读取四张目标表的 `TABLE_NAME / TABLE_TYPE / ENGINE`。兼容驱动返回的字符串、ASCII bytes 和引擎/类型首尾空白；只有四张名称准确且唯一的普通表、引擎明确为 InnoDB 才通过。未知值不会被默认当作 InnoDB。

失败消息区分缺失/账号不可见、重复或异常元数据、非普通表、已识别的非 InnoDB 引擎及未知引擎，并列出四张固定目标表的状态。不会输出数据库名、主机、账号、任意原始元数据或驱动异常内容。若 SQL 客户端显示四表正常而采集器仍失败，优先查看新报错中的“当前采集连接”状态，私下核对两端是否为同一连接配置和账号；不需要将凭证发到聊天，也不应先转换表引擎。

这项兼容修复并不证明现场错误必然来自 bytes。测试覆盖 MySQL 方言编译、专用初始化分支与 SQLAlchemy Row 返回结构，使用离线元数据样本；未连接生产库或替代真实 MySQL 权限/驱动联调。


## 全报告期历史恢复（当前可见修订历史）

独立入口只需本脚本和 `mysql_connector.py`，无需上传 `rules/` 或其他采集脚本。默认 `HISTORY_MODE='latest'` 不改变每日当前季度追加模式。要历史恢复，编辑脚本顶部：

```python
HISTORY_MODE = 'gaps'
START_PERIOD = None
MAX_PERIODS = 4
END_DATE = '2026-10-30'  # 示例：使用固定的历史截止日，按实际需求填写
```

也可在已载入函数的 Notebook 中执行：

```python
run(history_mode='gaps', start_period=None, max_periods=4, end_date='2026-10-30')
```

- `START_PERIOD=None` 从聚宽完整交易日历最早日期所属的报告季度开始**探测**，不是声称该日起财务表完整。脚本查询快报/预告当前账号可见的最早报告期，正式财报按季度键查询验证。可指定 `YYYY-03-31/06-30/09-30/12-31` 精确季末，不能任意日期。
- `MAX_PERIODS` 限制每次**尝试**的季度数，包含无法验证覆盖的季度，避免缺失早期数据造成无界扫描。默认 4；`None` 表示显式不限制。固定相同 `END_DATE` 重复执行 `gaps`，从尚未探测或尚未完成的季度继续。不要每次改变结束日，否则新的截止范围需要重新核查。
- `full` 表示在配置范围内重新核查历史，仍只追加、不覆盖任何成功股票快照。它会忽略已有探测标记；有限 `MAX_PERIODS` 时从 `START_PERIOD` 重新开始。要定点复核早期未知覆盖，使用 `full` 和指定起始季度，不需要删库。
- 批量入口 `STRATEGY_CONFIG['净利润断层']` 使用相同的 `history_mode`、`start_period`、`max_periods`、`end_date` 键；默认仍是 `latest`。

### 历史来源、时间边界与股票池

正式财报使用 `get_fundamentals(statDate='YYYYqN')`，按股票代码游标分页，并要求 `income`、`indicator` 报告期一致，两个发布日期均不晚于截止日；返回内容再次校验日期。快报/预告继续主键分页、报告期及发布日期过滤。这样读取旧季度，而不是用今天的 `date` 查询冒充旧季度数据，也不逐日重复查询几十年的财报。某期三条来源都没有可核实记录时，不能证明“零命中”，不会写入成功季度结果。

股票池在真实公告日期调用 `get_all_securities(date=公告日)`，验证上市和退市区间，按这些历史快照取并集；不使用今天的存续名单，因此可以包含后来退市的股票。公告当天已不在上市池的证券不构造可交易信号。行业按历史信号日期读取；估值仍按配置截止日，与每日原口径相同，已退市股票可能缺失估值，不补零。行情只读至最后相关公告后最多 20 个交易日或截止日，避免为几十年前的筛选下载整个后续价格历史。每日收盘跟踪仍独立执行。

入库事件中保存 `source_kind='joinquant_current_visible_history'`、`reconstruction_as_of`（实际重建日期）和 `historical_cutoff`。聚宽可能已经修订历史财报或复权价格，`statDate` 并不能恢复当年未修订版本；**这些是当前可见修订历史，不是最初抓取的 PIT 存档或严格无偏回测**。严格限制源表发布日期不会把截止日之后披露的行纳入，但无法证明源服务未在原发布日期下事后修订数值。公告交易日对应当日日线的既有方法不变，日期级数据仍不能区分盘前/盘后。历史修订被新发现时，不覆盖此前已经成功保存的股票。

### 检查点、失败与同步

`earnings_history_checkpoint` 独立保存每季度尝试的截止日、方法和更新时间。`quarter-visible-v2` 表示本次来源读取、追加事务及版本迁移成功；`unknown-empty-v2` 仅表示当次覆盖无法验证，不创建 `earnings_gap_run` 零命中记录，也不创建成功季度版本。`gaps` 在相同截止日会跳过并打印未知状态，便于继续后面的季度；`full` 可以重新验证。权限异常、缺字段、分页异常、股票池不可验证等直接中止当前季度，不把异常记成空结果。

网络采集在季度数据库事务之外完成。每个季度的新增股票、数量和结果版本通过现有锁与校验提交，之后才记录成功检查点；中断若发生在两次提交之间，下次安全追加重试，不删除已成功股票。历史运行不替换当前季度快照、不倒退较新的元数据。合法来源记录存在但筛选后无命中时，可以保存零命中季度。

历史恢复完成后，在网页“数据同步”同步净利润断层；旧季度沿用同样的版本协议和导入方式，无需新建另一套数据页。历史恢复不自动更新所有已选股票到今天的收盘表现，可随后运行每日 `latest` 入口刷新跟踪。代码与离线夹具验证不能证明某账号的聚宽权限、最早年份或线上实际覆盖；必须以研究环境执行结果及未知状态为准。源接口不提供的未修订公告版本、完整撤回/更正时间序列和逐笔披露时间，明确无法恢复。
