# 行业动量采集：保留最近 180 个交易日

采集脚本为 [collectors/行业动量计算_数据库版.py](../collectors/行业动量计算_数据库版.py)，在聚宽研究环境中运行。网页后端继续只读数据库，不负责删除或采集数据。

## 运行规则

每次运行先验证参数和聚宽交易日历，成功连接并确认表存在后，第一项数据修改就是清理过期记录，然后开始增量计算及入库。

- 用运行当天的北京时间调用 `get_trade_days(end_date=当天, count=180)`，以返回的最早交易日作为保留边界。周末和节假日使用截至当天的最近交易日，不按 180 个自然日计算。
- 删除 `industry_momentum` 中 `trade_date < 保留边界` 的所有记录；保留边界日及之后的记录。清理作用于整张表的所有行业分类，包含 `sw_l1/sw_l2/sw_l3`，零动量记录在保留范围内正常保留。
- 即使手动设置历史 `END_DATE`，保留边界仍以实际运行当天计算。如果结束日期早于保留范围，只执行清理，不重新写入过期数据。
- 查询清理后的最后入库日，从该日（含）继续更新；当天重跑仍替换完整日快照，避免重复行和旧行业残留。
- 首次入库或该分类的旧记录已全部清理时，从 `START_DATE` 和保留边界中较晚的日期开始。`START_DATE = '2025-01-01'` 不会让已清理数据重新写回。

`RETENTION_TRADE_DAYS = 180` 为默认保留数量。180 个交易日一般不足一年，网页的“近一年”图表只能展示保留范围内的已有数据；保留策略不会自动补齐缺失交易日，也不会改变动量计算公式。

## 失败处理与事务

保留日历为空、不足 180 天、重复、乱序或包含未来日期时，程序在修改数据库前停止。DELETE 使用单独事务，失败回滚并停止后续计算；清理成功会打印删除行数和保留起始日期。

清理提交后才开始逐日计算，各日仍使用独立事务入库。后续行情获取或写入失败不会撤销已经完成的清理；再次运行只在保留范围内继续更新。不要并发运行多个采集实例。

## 聚宽运行方法

GitHub 副本中的 `MysqlMomentum` 连接字段均为占位值。请在聚宽的私有副本中填写与原策略相同的数据库连接信息，数据库账号需要现有入库权限以及 DELETE 权限。不要把填入真实密码后的文件提交回 Git。

这个独立聚宽脚本不自动读取网页服务器的 `config/app.config`。已有本地原策略的连接信息在此次修改中予以保留。

沿用已有研究环境 API 导入方式，可直接在 Notebook 粘贴运行，或执行：

```python
%run -i 行业动量计算_数据库版.py
```

日志首先显示清理情况，然后显示当天或待补录交易日的计算、写入结果。只有实际在聚宽运行脚本时才会执行数据库清理；本次开发验证使用独立 SQLite，不清理真实 MySQL。
