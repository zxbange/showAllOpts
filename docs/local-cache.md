# 本地缓存与数据同步

## 为什么使用磁盘快照

公网 MySQL 的连接和往返延迟会叠加到每个页面查询。本项目默认把九个模块实际展示的表复制到本机 SQLite，再由原来的 repository/service 执行筛选、排序、分页和历史查询。缓存包含历史数据与详情，不只缓存首页响应。SQLite 使用本机磁盘和操作系统文件缓存，无需安装 Redis；后端重启后仍可使用快照。

本地缓存减少公网等待，不承诺特定毫秒数；页面图表渲染和访问服务器的网络仍影响速度。关闭缓存可回到原来的直接查询模式。

## 配置

Linux 原生部署使用 `config/app.config`，Windows 默认 `backend/.env`，Docker 继续使用 Compose 的配置文件。已有配置未添加以下项时也采用默认值：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `CACHE_ENABLED` | `true` | 启用本地快照；false 时页面直连源数据库 |
| `CACHE_AUTO_REFRESH` | `true` | 每天定时同步；启动不补跑 |
| `CACHE_REFRESH_TIME` | `07:00` | 北京时间，24小时制 HH:MM；与服务器系统时区无关 |
| `CACHE_DB_READ_TIMEOUT` | `600` | 后台同步数据库 socket 读取超时，秒，范围5～3600；不是整个同步任务的总时限 |
| `CACHE_SYNC_ATTEMPTS` | `3` | 单个模块连接失败/中断时的总尝试次数，范围1～5；1表示不重试 |

每日时间可在页面“数据同步 → 自动同步时间”编辑并保存（`HH:mm`，北京时间），不用重启。`POST /api/v1/cache/schedule` 接收 `{"daily_time":"07:00"}`；权限与现有手动同步接口一致。`GET /api/v1/cache/status` 返回当前 `daily_time`、`timezone` 和 `next_refresh_at`（自动同步关闭时为空）。不会调用源库、开启已关闭的自动同步或触发即时同步。两融等独立采集计划不受影响。

时间优先级：页面已保存值 > 环境变量/配置文件中的非旧默认时间 > 默认07:00。页面设置原子保存至 `LOG_DIR/cache/schedule.json`，与模块同步的状态文件分开，不受同步发布或数据库缓存签名变化覆盖；同一目录的所有worker共享，重启后保留。需持久化整个缓存目录。保存失败会明确提示，原设置保留；设置文件损坏不会静默退回默认值。

升级兼容：没有页面保存记录时，旧 `CACHE_REFRESH_TIME=20:00` 被视为旧默认，实际按07:00执行，不修改私有配置文件；其他显式时间（例如18:00）保留。历史文件无法区分“旧默认20:00”和“主动选择20:00”，如仍希望20:00，请在页面明确保存一次；此后它优先于所有环境变量。普通环境变量/配置修改仍需重启，且不会覆盖页面保存值。

调度每约30秒读取共享设置。改到尚未到达的时间，下一次在该时间运行；改到已经到达的时间（含当前分钟零秒），从次日执行。北京时间同一日已认领过定时任务，修改时钟不会重复运行；手动全部同步沿用占用最近时段的行为。保存时正在进行的同步继续，不取消也不重启。服务启动不补跑停机错过的时段；当天失败/中断仍沿用现有不自动补跑规则。

网页手动同步无需配置或输入密钥。旧配置中的 `CACHE_REFRESH_TOKEN` 已不再使用，保留或删除均不影响运行。

快照和协调文件位于 `${LOG_DIR}/cache/<来源与结构指纹>/`，默认项目 `log/cache/`。指纹不包含密码；更换数据库、账号或模型结构会建立新命名空间。已有 systemd `ReadWritePaths` 和 Docker 的日志卷覆盖该位置。不要把缓存目录配置为 Nginx 的静态目录；它不是公开下载文件。

## 自动更新规则

- 首次启动没有快照时，请在页面手动同步，或等待服务运行期间的下一个07:00。已经完成的模块即可打开，未完成的模块返回明确的“本地数据尚未准备好”。页面请求不触发额外 MySQL 查询。
- 每天北京时间 07:00 同步全部模块，调度检查间隔约30秒。应用必须在运行；启动不补跑停机错过的周期。
- 重启时已有当前周期的快照直接使用，避免每个 worker 都重新采集。即使只有一个模块失败，其他模块仍可完成。
- 已有快照的模块同步失败时继续展示旧数据，面板标明失败和上次成功时间；可手动重试，或等下次每日同步。缺失快照也不在启动后自动重试。
- 通常同一模块的多张表使用同一源事务读出（机构持仓首次全量续传跨尝试时以变更记录最终补差）；所有复制、校验完成后才切换新快照。中途断连、写盘失败不会用半份数据覆盖旧快照。一次成功读取到空表是有效空结果，会替换旧数据。
- MySQL 连接错误2003、2006、2013、2055会有限重试，默认总共尝试3次，间隔2秒、4秒。除机构持仓全量续传会保留已提交的分页断点外，每次失败丢弃未发布的本地副本，重新建立源事务，从上次成功缓存重新计算差异；不会沿用失败的一半结果。服务关闭可中断重试等待，未处理模块可由下次手动同步继续，或等待下一次定时同步。认证、表结构、本地磁盘错误直接报告，不重复重试。
- 自动任务、网页与 CLI 共用跨进程文件锁，同一目录同时只允许一个任务。操作系统在进程退出时释放锁，残留锁文件不表示任务仍在运行；中断时未处理模块会在下次运行继续。
- 生成新 SQLite 文件后原子切换元信息。正在查询旧文件的请求可以继续完成；非当前版本且超过24小时的文件在后续同步结束时清理。切换来源/结构遗留的旧命名空间可在维护时人工归档，不自动递归删除。

## 增量同步规则

首次没有缓存时读取源表全部现存历史；已有快照（包括旧版本生成的快照）默认增量同步，网页按钮、每日任务与 CLI 使用相同规则。现有日期范围、筛选与股票详情保持可用。

| 模块 | 后续同步方式 |
| --- | --- |
| 行业动量、抱团拥挤度、ETF份额、微盘新高新低 | 按各分区的日期水位追加；历史修订或删除需完整同步 |
| 市场情绪、微盘温度计、ETF动量热度 | 新采集器在业务写入的同一事务提交变更键和 generation/revision；版本不变直接跳过，变化时只拉取涉及的键，支持补洞、历史修复和删除 |
| 净利润断层 | 比较小型季度头与季度版本；未变化季度不查股票清单，追加版本只检查该季度主键并下载新增股票；整季重建改变 generation，完整替换该季度 |
| 短线选股 | 比较保留日期的完整运行头（含 JSON、快照版本和更新时间），变化日期的头与全部明细一起替换；升级首次只重建此模块，修复历史头与明细不同步 |
| 个股机构持仓 | 沿用事务变更日志；版本不变直接跳过，缺少协议时兼容对账 |
| 高增长、高股息选股 | 每次读取完整最新名单，移除退出名单股票 |

网页、每日任务与 CLI 共用上述路径。首次无缓存、代际变化或显式 `--full` 会建立完整基线。市场情绪、微盘温度计和 ETF 热度的日志必须连续；缺口、非法记录或缺失源记录会保留旧快照并报错，完成源库检查后可以完整同步重新建立基线。数据与游标写入同一 SQLite 事务，完成后才原子发布；失败重试从最后成功游标继续，未完成基线重新读取，不保留半份结果。

**升级采集端：** 请完整替换聚宽独立脚本及批量脚本中所有实际使用的副本。新脚本自动创建 `result_sync_head`、`result_sync_change`，净利润断层创建 `earnings_sync_head`，需要相应建表和写入权限。原业务表结构不变。升级时先停止旧采集任务，发布支持新协议的服务，再替换所有在用的独立和批量采集脚本；运行新版采集器成功后，在页面同步相应模块。首次启用协议建立一次基线，此后才能跳过无变化模块。日志暂不自动清理。

旧源库缺少日志或季度版本时继续使用原全清单对账，页面显示升级提示，不会直接改成可能漏历史补录的日期追加。**启用协议后不能混用旧采集器或绕过协议人工写入**：这些写入不能推进版本，无法由无变化检查发现。需要人工修复时使用新版写入路径，或在修复后完整同步；季度已有股票内容修订须走整季重建。兼容路径仍受旧 `updated_at` 精度限制，同秒改写可用完整同步修复。

短线采集只有规则版本正确、四种策略计数均为非负整数且与明细一致时才跳过已有日期。缺少 `oversold` 计数仍表示未计算，不会补成零；再次运行新版采集器会重新计算该日。每次实际重建还生成独立快照版本，即使同秒重算后计数相同也能被同步识别。仅升级网页不能为源库尚未计算的策略生成结果。

MySQL 使用同一 REPEATABLE READ 源事务读取头、日志和结果；本地复制完成前继续服务旧快照。批量写入在读取受影响主键前锁定模块版本，并对主键查询使用当前锁定读，防止并发写入造成漏记。详情按最多250个主键一组读取；全量读取按主键分页，无递增 OFFSET。缓存历史范围仍以源数据库为准，不额外截短。

## 手动更新

网页右上角点击“本地数据 / 数据同步”，查看各模块状态。在“同步范围”中选择一个模块或全部模块，直接点击“立即同步”，无需密钥。同步进行中禁用按钮与范围选择，后端共享文件锁阻止重复启动。HTTP 请求立即返回，后台继续运行；同步完成后已打开页面会自动重新读取快照。同步期间普通查询仍读取旧快照。

页面中各模块原有的刷新按钮仅重新读取当前快照。数据库中刚采集的数据，需要自动或手动同步后才能在页面出现；“同步时间”也不等于“交易日”，实际数据日期以各模块内容为准。

Linux 命令行（以与服务相同的账号执行，不加 sudo）：

```bash
cd /home/ubuntu/showAllOpts
backend/.venv/bin/python scripts/refresh_cache.py
backend/.venv/bin/python scripts/refresh_cache.py --module industry-momentum
backend/.venv/bin/python scripts/refresh_cache.py --status
# 人工修订历史数据但未更新标记，或需修复本地缓存时，强制全量重建
backend/.venv/bin/python scripts/refresh_cache.py --module industry-momentum --full
# 服务使用自定义配置文件时，CLI 同样指定该文件
backend/.venv/bin/python scripts/refresh_cache.py --env-file config/app.config
```

Windows PowerShell：

```powershell
.\backend\.venv\Scripts\python.exe scripts/refresh_cache.py
.\backend\.venv\Scripts\python.exe scripts/refresh_cache.py --status
.\backend\.venv\Scripts\python.exe scripts/refresh_cache.py --module industry-momentum --full
```

CLI 默认全部同步，也可以只同步下列模块之一：

| 模块 ID | 名称 |
| --- | --- |
| industry-momentum | 行业动量 |
| market-crowding | 抱团拥挤度 |
| microcap-temperature | 微盘温度计 |
| etf-shares | ETF份额仪表盘 |
| earnings-gap | 净利润断层 |
| microcap-breadth | 微盘新高新低 |
| dividend-selection | 高股息选股 |
| high-growth | 高增长 |
| etf-momentum | ETF动量热度 |

CLI 默认增量同步；`--full` 可重建所选模块，不指定 `--module` 时重建全部模块，无需删除缓存目录。同步过程与结果打印到控制台，并使用现有应用日志，其中记录全量/增量模式、下载条数和删除条数（断层记录变化季度数及下载条数）。退出码0表示所选模块全部完成，1表示失败，2表示已有任务在执行。`--status` 只读取本地状态，不连接 MySQL。网页同步返回202仅表示任务已接受，最终结果以状态面板为准。

## 部署、只读与故障排查

升级仍执行 `bash deploy.sh`；Windows 更新后重启 `start.cmd`。无需新增定时服务或端口，无需重建 MySQL 表，不写入或清理源数据库。新增 Python 导入 `portalocker`，项目锁定依赖已包含该包。所有建表、索引与数据写入均发生在本地 SQLite；MySQL 账号保持只读权限即可。

同步失败时，面板显示脱敏错误码和对应提示；`log/error.log` 记录 `module`、`error_type`、`code`、`hint` 与 `frames`（文件名、行号、函数名），不打印 SQL、参数、原始驱动错误或连接凭据。`log/app.log` 还记录轻量清单读取开始及待增删条数，用于区分清单读取与后续数据传输阶段。

Linux 查看行业动量最近的失败记录：

```bash
cd /home/ubuntu/showAllOpts
grep 'Cache refresh failed module=industry-momentum' log/error.log | tail -n 3
```

自定义 `LOG_DIR` 时替换日志目录。常见错误码：

| 错误码 | 排查方向 |
| --- | --- |
| `MYSQL_2013` / `MYSQL_2006` | 源库连接中断或读取超时；后台已使用分页和有限重试。持续失败时检查公网链路、源查询耗时及数据库负载，必要时调整 `CACHE_DB_READ_TIMEOUT`；不能仅凭此码断定缺索引 |
| `MYSQL_1045` / `MYSQL_1142` | 服务使用的配置、账号认证或 SELECT 权限 |
| `MYSQL_1054` / `MYSQL_1146` | 采集器与项目的字段、表是否一致，是否连接到正确数据库 |
| `SQLITE_READONLY` / `SQLITE_CANTOPEN` / `OS_13` | 服务账号对缓存目录及文件的读写权限、所有者、systemd 可写路径 |
| `SQLITE_FULL` / `OS_28` | 缓存盘剩余空间 |
| `SQLITE_CORRUPT` / `SQLITE_NOTADB` | 本地缓存损坏；可在同一运行账号下对该模块执行 `--full` 重建 |
| `UNKNOWN` | 检查日志 `error_type` 与 `frames`；不要根据通用提示猜测原因 |

- 首次一直待同步：查看 `log/error.log` 中对应模块和异常类型，确认数据库连接、新模块的表已由聚宽采集器建立且账号有 SELECT 权限。
- 最新数据未出现：确认聚宽已完成入库，检查面板“上次成功同步”，再手动同步。07:00之后才入库的数据会等到下次同步；可修改时间或手动更新。
- CLI 成功、网页仍旧：确认 CLI 和 systemd 使用相同账号、配置、数据库、`LOG_DIR` 和源码版本。原生部署与 Docker 若是不同运行环境，应在实际服务环境中执行同步。
- 手动同步仍提示输入密钥或返回403：前后端版本尚未全部更新。Linux 执行 `bash deploy.sh`；Windows 更新代码后重启 `start.cmd`，再刷新浏览器。
- 409：已有任务执行，或缓存已关闭。等待状态变为空闲再操作。
- 本地快照读取失败：先手动同步该模块，检查磁盘空间和目录权限；不要直接编辑 SQLite 文件。若需要重建缓存，先停止服务和同步命令，再备份并移走对应缓存目录，重启后手动同步重新准备。
- 定时任务不运行：确认 `CACHE_AUTO_REFRESH=true`、应用未停止、配置时间正确；调度固定使用北京时间。

公网数据库断开时已有本地快照仍能展示；但首次同步或手动刷新需要数据库连通。缓存数据可能过期，面板明确显示同步时间和失败状态；页面不会静默回源。`CACHE_ENABLED=false` 并重启可恢复旧的直连行为。

### 行业动量读取超时（MySQL 2013）

若堆栈位于 `cache_sync.read_map` / PyMySQL `fetchmany`，并显示 `Lost connection to MySQL server during query (timed out)`，表示从源库读取对比清单时等待网络数据超时。后续清理断开的流式游标可能再报 `NoneType ... read`，应先处理前面的2013错误。旧版本后台同步沿用20秒读取超时，新版本使用上述后台专用超时、主键分页和有限重试；关闭缓存后的直接页面查询仍保持20秒读取超时。

Linux 在项目根目录执行 `bash deploy.sh` 更新并重启后端，再到页面仅同步“行业动量”验证。已有配置不添加新项也会采用600秒、3次的默认值。如需覆盖，在 `config/app.config` 添加以上参数并重启 `showallopts-api`。不要直接删除源数据或现有缓存；失败时旧缓存会继续服务。若持续出现2013，请提供日志中带 `code`、`frames` 的失败行及 `Cache refresh retry` 行，以检查具体失败阶段；延长客户端超时无法修复持续断网或数据库服务端主动断开。


## 个股机构持仓的变更序号同步

新版聚宽采集器维护事务性的变更序号和主键记录，本模块不再扫描全历史主键及更新时间。首次/升级建立一次完整基线，之后按序号查询新增、更正和删除；未变化时直接结束。所有写入须使用新版脚本，人工 SQL 改库后用 `--module institution-ownership --full` 复核。旧库没有变更表时兼容原扫描流程。详见 [机构持仓同步加速](institution-ownership.md#本地同步加速)。

### 大数据量同步超时

后台读取默认 600 秒，可设置 `CACHE_DB_READ_TIMEOUT=1800` 延长至 30 分钟，最大 3600 秒。这是数据库 socket 单次读取等待上限，不是整个同步任务的总时限；持续收到数据的任务可以运行更久。同步在后台执行，网页只提交任务和查询进度，无需为此延长 Nginx 请求超时。建立数据库连接仍为 8 秒，关闭缓存后的页面直查仍为 20 秒。

Linux 修改 `config/app.config`，Windows 修改 `backend/.env`；如设置 `APP_ENV_FILE`，修改其指定文件。修改后重启后端。旧配置若显式设置 `CACHE_DB_READ_TIMEOUT=120`，需要改为 600，显式配置优先于默认值。提高超时也会延长发现网络故障及等待同步线程退出的时间，不能修复服务端主动断开的问题。

同步进度跨进程共享，每个模块显示等待、运行、完成、失败或中断。运行中展示阶段、累计处理行数（含对比读取与重试，并非唯一新增行数）和耗时；按阶段显示百分比，只有快照成功完成才到100%；等待0%、准备5%、表同步10%～90%、校验95%。表同步阶段按表数分段，已知增量条数时进一步按已写入条数推进。重试时保留已达阶段百分比并显示重试状态；这是阶段进度，不是任务剩余时间或总行数百分比。状态按批次节流写入，不额外执行源库 COUNT 查询。

### 排查 Sending to client 与同步耗时

MySQL 的 `Sending to client` 表示服务端正在向客户端写数据包，单凭该状态不能断定 SQLite 写盘慢。当前同步使用缓冲式主键分页，每页完整接收并关闭结果后才写入本地；不在流式游标尚未读取完毕时写盘。公网吞吐、丢包或接收端 CPU 等都需要结合实际耗时排查。

JSON 结果直接以文本搬运至 SQLite，省去同步阶段 JSON 解析和重新序列化，页面查询时仍按原结构解析。不改变源表、历史数据或增量游标，也不需要重新采集。直接文本搬运降低客户端转换开销；机构持仓另支持默认开启的 JSON 压缩传输，减少公网字节量。

在 `log/app.log` 中搜索 `Cache transfer`：`read_seconds` 包含查询执行、网络接收、驱动和结果转换；`prepare_seconds` 为构造写入参数；`write_seconds` 为 SQLite 批量 INSERT 执行时间（不含最终事务提交、文件复制和校验）。不要将读取耗时单独解释为网络耗时。`Cache manifest` 记录主键/更新时间对比读取，`Cache slow read` 记录超过5秒的单页读取。日志只含表名、计数和耗时，不含业务 JSON 或数据库连接信息。

```bash
grep -E 'Cache transfer|Cache manifest|Cache slow read|Cache read failed' log/app.log | tail -n 50
```

若读耗时占主导，优先检查实际源查询、公网链路和客户端 CPU；若写耗时占主导，检查本地磁盘负载。无需因线程状态直接扩大超时或开启更多并行同步连接。

机构持仓首次全量支持断点续传：详见 [首次全量同步断点续传](institution-ownership.md#首次全量同步断点续传)。请保留缓存目录内的 `.partial` 文件；未成功的单页会重新下载，已提交页可以复用，最终补差与校验通过才供页面读取。

机构持仓压缩传输开关 `CACHE_OWNERSHIP_COMPRESSION=true` 默认生效，详情见 [传输与本地写入优化](institution-ownership.md#公网传输与本地写入优化)。开关不影响既有缓存和续传断点。
