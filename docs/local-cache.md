# 本地缓存与数据同步

## 为什么使用磁盘快照

公网 MySQL 的连接和往返延迟会叠加到每个页面查询。本项目默认把七个模块实际展示的表复制到本机 SQLite，再由原来的 repository/service 执行筛选、排序、分页和历史查询。缓存包含历史数据与详情，不只缓存首页响应。SQLite 使用本机磁盘和操作系统文件缓存，无需安装 Redis；后端重启后仍可使用快照。

本地缓存减少公网等待，不承诺特定毫秒数；页面图表渲染和访问服务器的网络仍影响速度。关闭缓存可回到原来的直接查询模式。

## 配置

Linux 原生部署使用 `config/app.config`，Windows 默认 `backend/.env`，Docker 继续使用 Compose 的配置文件。已有配置未添加以下项时也采用默认值：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `CACHE_ENABLED` | `true` | 启用本地快照；false 时页面直连源数据库 |
| `CACHE_AUTO_REFRESH` | `true` | 启动后台准备、缺失快照重试和每天定时同步 |
| `CACHE_REFRESH_TIME` | `18:00` | 北京时间，24小时制 HH:MM；与服务器系统时区无关 |
| `CACHE_REFRESH_TOKEN` | 空 | 网页手动同步密钥，空值时拒绝网页触发；不影响自动同步和命令行 |

修改配置后重启后端。密钥只放真实配置，设置长随机值，例如用 Python 的 `secrets.token_urlsafe(32)` 在服务器本地生成后填入；不放 URL、前端代码或 Git。浏览器仅在请求头发送密钥，不保存到 localStorage/sessionStorage。对外访问使用 HTTPS 可保护传输中的密钥。

快照和协调文件位于 `${LOG_DIR}/cache/<来源与结构指纹>/`，默认项目 `log/cache/`。指纹不包含密码；更换数据库、账号或模型结构会建立新命名空间。已有 systemd `ReadWritePaths` 和 Docker 的日志卷覆盖该位置。不要把缓存目录配置为 Nginx 的静态目录；它不是公开下载文件。

## 自动更新规则

- 首次启动没有快照，后台立即按顺序同步全部模块。已经完成的模块即可打开，未完成的模块返回明确的“本地数据尚未准备好”。页面请求不触发额外 MySQL 查询。
- 每天北京时间 18:00 同步全部模块，调度检查间隔约30秒。应用必须在运行；停机错过的周期在下一次启动时补做最近一次，不逐日重放。
- 重启时已有当前周期的快照直接使用，避免每个 worker 都重新采集。即使只有一个模块失败，其他模块仍可完成。
- 已有快照的模块同步失败时继续展示旧数据，面板标明失败和上次成功时间；可手动重试，或等下次每日同步。缺失快照的模块每5分钟后台重试一次。
- 同一模块的多张表使用同一源事务读出；所有复制、校验完成后才切换新快照。中途断连、写盘失败不会用半份数据覆盖旧快照。一次成功读取到空表是有效空结果，会替换旧数据。
- 自动任务、网页与 CLI 共用跨进程文件锁，同一目录同时只允许一个任务。操作系统在进程退出时释放锁，残留锁文件不表示任务仍在运行；中断时未处理模块会在下次运行继续。
- 生成新 SQLite 文件后原子切换元信息。正在查询旧文件的请求可以继续完成；非当前版本且超过24小时的文件在后续同步结束时清理。切换来源/结构遗留的旧命名空间可在维护时人工归档，不自动递归删除。

按模块复制的是源表全部现存历史，而不是只取当天或只取最近一年；因此现有日期范围、净利润断层筛选和股票详情仍可用。每次刷新重新复制模块完整快照，也能反映源数据清理、修订与高股息整组替换，避免仅按最大日期追加造成旧数据无法纠正。采用2000行分批传输；行业成分股名单和已删除的断层原因分析字段不传输，网页需要的公告、K线 JSON 仍保留。

## 手动更新

网页右上角点击“本地数据 / 数据同步”，查看各模块状态。配置了密钥后可选一个模块或全部模块，输入密钥并执行“立即同步”。HTTP 请求立即返回，后台继续运行；同步完成后已打开页面会自动重新读取快照。同步期间普通查询仍读取旧快照。

页面中各模块原有的刷新按钮仅重新读取当前快照。数据库中刚采集的数据，需要自动或手动同步后才能在页面出现；“同步时间”也不等于“交易日”，实际数据日期以各模块内容为准。

Linux 命令行（以与服务相同的账号执行，不加 sudo）：

```bash
cd /home/ubuntu/showAllOpts
backend/.venv/bin/python scripts/refresh_cache.py
backend/.venv/bin/python scripts/refresh_cache.py --module industry-momentum
backend/.venv/bin/python scripts/refresh_cache.py --status
# 服务使用自定义配置文件时，CLI 同样指定该文件
backend/.venv/bin/python scripts/refresh_cache.py --env-file config/app.config
```

Windows PowerShell：

```powershell
.\backend\.venv\Scripts\python.exe scripts/refresh_cache.py
.\backend\.venv\Scripts\python.exe scripts/refresh_cache.py --status
```

CLI 默认全部同步，也可以只同步下列模块之一：

| 模块 ID | 名称 |
| --- | --- |
| industry-momentum | 行业动量 |
| market-crowding | 抱团拥挤度 |
| microcap-temperature | 微盘温度计 |
| etf-shares | ETF份额仪表盘 |
| earnings-gap | 净利润断层 |
| microcap-breadth | 微盘新高新低 |
| dividend-selection | 高股息选股 |

CLI 同步过程与结果打印到控制台，并使用现有应用日志。退出码0表示所选模块全部完成，1表示失败，2表示已有任务在执行。`--status` 只读取本地状态，不连接 MySQL。网页同步返回202仅表示任务已接受，最终结果以状态面板为准。

## 部署、只读与故障排查

升级仍执行 `bash deploy.sh`；Windows 更新后重启 `start.cmd`。无需新增定时服务或端口，无需重建 MySQL 表，不写入或清理源数据库。新增 Python 导入 `portalocker`，项目锁定依赖已包含该包。所有建表、索引与数据写入均发生在本地 SQLite；MySQL 账号保持只读权限即可。

- 首次一直待同步：查看 `log/error.log` 中对应模块和异常类型，确认数据库连接、新模块的表已由聚宽采集器建立且账号有 SELECT 权限。
- 最新数据未出现：确认聚宽已完成入库，检查面板“上次成功同步”，再手动同步。18:00之后才入库的数据会等到下次同步；可修改时间或手动更新。
- CLI 成功、网页仍旧：确认 CLI 和 systemd 使用相同账号、配置、数据库、`LOG_DIR` 和源码版本。原生部署与 Docker 若是不同运行环境，应在实际服务环境中执行同步。
- 403：未配置密钥或输入错误；本接口不会公开允许任意访客触发数据库同步。
- 409：已有任务执行，或缓存已关闭。等待状态变为空闲再操作。
- 本地快照读取失败：先手动同步该模块，检查磁盘空间和目录权限；不要直接编辑 SQLite 文件。若需要重建缓存，先停止服务和同步命令，再备份并移走对应缓存目录，重启后会重新准备。
- 定时任务不运行：确认 `CACHE_AUTO_REFRESH=true`、应用未停止、配置时间正确；调度固定使用北京时间。

公网数据库断开时已有本地快照仍能展示；但首次同步或手动刷新需要数据库连通。缓存数据可能过期，面板明确显示同步时间和失败状态；页面不会静默回源。`CACHE_ENABLED=false` 并重启可恢复旧的直连行为。
