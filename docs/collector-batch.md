# 聚宽模块化批量采集

`collectors/策略批量采集_数据库版.py` 是统一入口，五个数据库版文件各自作为一个策略模块。入口使用 Python 模块加载器依次调用各模块的 `run()`，不再嵌入源码，也不需要构建或生成批量文件。兼容 Python 3.6 语法，沿用聚宽、pandas、SQLAlchemy 和 MySQLdb 环境。

## 上传与运行

将下面 **6 个文件一起上传到聚宽研究环境的同一目录**，保持文件名不变：

```text
策略批量采集_数据库版.py       # 入口：统一配置、串行调用、控制台结果
行业动量计算_数据库版.py       # 行业动量模块
抱团拥挤度_数据库版.py         # 拥挤度模块
微盘温度计_数据库版.py         # 微盘温度计模块
ETF份额_数据库版.py            # ETF 份额模块
净利润断层_数据库版.py         # 净利润断层模块
```

1. 在入口文件顶部 `DB_CONFIG` 填写私有数据库连接。批量调用时会统一注入五个模块，无需逐个修改模块里的连接配置。GitHub 只保留占位值。
2. Notebook 切换到上述目录，执行：

   ```python
   %run -i 策略批量采集_数据库版.py
   ```

   `-i` 让入口沿用 Notebook 提供的聚宽 API，再传递给各模块。策略文件按入口所在目录查找。**新版不能只上传入口，也不再支持只粘贴入口代码运行。**
3. 查看各策略完成后的结果及末尾汇总；`batch_summary` 保存策略名称、状态、实际新增条数、耗时、脱敏错误信息。

本机 `original/` 下也已同步这六个文件，并保留原有私有数据库连接，位于 Git 仓库之外。采集需要在聚宽研究环境运行，Linux 网页后端继续负责读取数据库；仅更新采集脚本无需重新发布网页。

## 执行顺序与数据规则

默认顺序为：**行业动量 → 抱团拥挤度 → 微盘温度计 → ETF份额 → 净利润断层**。同一时间只执行一个策略；每个策略拥有独立命名空间，避免 `run`、`Base`、日期参数和其他同名对象相互覆盖。

批量入口固定传入 `skip_existing=True`，只写入业务主键尚不存在的数据，不再覆盖最新一天或 ETF 回查窗口。已有行即使源数据发生变化也保留原值。

| 策略 | 批量入口的采集、清理规则 |
| --- | --- |
| 行业动量 | 先清理整张表 180 个交易日前的数据，再从该分类最新入库日之后采集；已有日期不重算 |
| 抱团拥挤度 | 从当前 TOP_PCT 最新入库日之后采集，保留完整历史 |
| 微盘温度计 | 保留 2021-01-01 起、每 5 个交易日采样；以已保存最新一期为基准继续，不改变采样间隔；保留历史 |
| ETF份额 | 首次最近 300 个交易日；每只基金从自己的最新入库日之后续传，不再回查或覆盖最近 5 日；保留历史 |
| 净利润断层 | 扫描最新已结束季度中尚未入库的股票；按“报告期＋股票代码”只新增，已入库股票保留首次快照，不覆盖、不删除 |

控制台中的条数是实际新增业务记录数；没有新增数据会输出“无新增数据（已有记录跳过，或本次尚无可入库数据）”。唯一键仍用于兜底；如果其他独立任务并发抢先写入导致冲突，该事务回滚后报告失败，不通过删除旧记录解决冲突。

净利润断层的市值、PE、PB、信号日期及公告信息保留首次入库时的值，不随以后运行刷新。其 `earnings_gap_run` 运行元数据仅在扫描截止日、累计股票数等内容变化时更新，重复运行且内容不变时也不写入；汇总中的新增条数只统计股票明细。页面的扫描截止日不代表每只股票的估值日期，应以股票自身的 `valuation_date` 为准；“命中数”表示该季度累计保留数量，不是当次重新筛选的数量。

行业动量、抱团拥挤度和微盘温度计在只新增模式下，北京时间 16:00 前不写当天日数据，避免盘中快照被永久保留。净利润断层沿用已有完整交易日规则；ETF 以数据源实际发布为准。历史已写入的不完整值或源后续修订不会自动纠正，更早缺口也不会因为从最新日期续传而自动补齐。

独立策略的 `run()` 为兼容原用法，默认仍是原先的覆盖刷新模式；如需单独运行也遵循只新增规则，显式调用 `run(skip_existing=True)`。常规任务使用模块化批量入口即可，不要再同时运行旧版单策略脚本。批量入口不允许通过参数关闭 `skip_existing`。

## 控制台结果与失败处理

入口不生成日志目录或日志文件，不显示各模块逐日、逐窗口的过程输出。每个策略完成后显示名称、成功/失败、实际新增条数和耗时，并预览最后 5 条新增数据的关键字段；没有新增数据时明确提示。字段名和单位沿用各策略：ETF `shares` 为份，温度计 `score` 为原始 0–1 分值。设置 `PREVIEW_ROWS = 0` 可关闭数据预览，只看汇总。

```text
【行业动量】成功：新增 124 条，耗时 3.10 秒。
本次新增结果（最后 5 条，字段单位沿用策略）：
...
【净利润断层】成功：新增 0 条，耗时 2.20 秒。
无新增数据；已有记录跳过，或数据源尚无可入库数据。

采集结果汇总
策略 | 结果 | 新增条数 | 耗时（秒）
行业动量 | SUCCESS | 124 | 3.10
...
净利润断层 | SUCCESS | 0 | 2.20
成功 5，失败 0。
```

- 长时间首次采集时，策略完成前没有过程输出，Notebook 仍会显示正在执行。
- 普通异常在控制台展示脱敏后的类型和简要原因，然后继续后续策略；失败策略新增条数标为“未完成”，不会误报为 0。最后默认抛出 `BatchRunError`，其 `summary` 属性保留结果。
- 各模块独立提交事务，**不会整个批次一起回滚**。失败前已成功入库的数据、已完成的过期清理保留，修复后只补新增数据。
- Notebook 中断会停止整个批次，不再执行后续策略。
- 保留同目录互斥，入口旁的 `.collector-batch.lock` 仅是运行锁，不是日志；进程退出自动释放，文件留存不表示仍在运行。不要删除运行中的锁，也不要同时通过独立脚本、其他目录或其他研究容器采集同一批数据。
- 网页服务的 `log/` 日志功能不受影响；独立策略直接运行时仍保留原有输出方式。需要本页的安静输出和只新增规则，请统一使用此入口。

## 只运行部分策略或调整参数

可修改入口顶部的 `STRATEGY_ORDER`，仅保留需要的策略，顺序就是调用顺序。例如只执行净利润断层：

```python
STRATEGY_ORDER = ['净利润断层']
```

已通过 `%run -i` 加载入口后，也可以在 Notebook 中调用：

```python
# 只重跑两个策略，按给出的顺序串行执行
batch_summary = run_all(strategy_names=['ETF份额', '净利润断层'])

# 展示汇总，不预览新增数据；有失败时不抛出批次异常，供手动检查
batch_summary = run_all(preview_rows=0, raise_on_failure=False)

# 只采集沪深300 ETF；run() 参数通过策略名称传入
batch_summary = run_all(
    strategy_names=['ETF份额'],
    options={'ETF份额': {'groups': ['hs300']}},
)
```

默认 `STRATEGY_OPTIONS = {}` 保持各策略原参数。不要随意改变微盘温度计起始日期、数量或采样步长，这些参数会生成不同序列，同日期不同序列不属于重复记录。

## 维护方式

业务逻辑只维护各自的策略模块，更新后上传修改过的文件即可；每次运行都会重新加载模块。增加策略时，在入口 `STRATEGIES` 登记文件名和数据库连接类名、在 `STRATEGY_ORDER` 指定顺序、在 `_PREVIEW_COLUMNS` 指定展示字段。模块须提供 `run(skip_existing=True, ...)`，并返回本次实际新增记录的 DataFrame。

旧版源码嵌入模板和生成脚本已删除，不再执行 `build_collector_batch.py`。离线测试覆盖模块隔离与重载、Notebook API 传递、串行顺序、只新增约束、结果预览、异常继续、凭据脱敏和互斥；真实聚宽接口权限及 MySQL 连通性需在研究环境中验证。
