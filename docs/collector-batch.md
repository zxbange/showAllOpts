# 聚宽单文件批量采集

`collectors/策略批量采集_数据库版.py` 包含五个完整策略，依次串行调用。依赖统一在文件开头导入，参数按策略集中配置；数据库连接、重试、会话回滚关闭和日期转换共用一套实现。每个策略保留独立模型和计算函数，代码直接定义在文件中，不把源码存成字符串，也不使用 `exec` 动态执行。

**运行时不读取其他策略文件、配置文件或日志文件，不使用 `__file__`，也不创建日志或锁文件。** 仍需聚宽研究平台自带的 API，以及 pandas、SQLAlchemy、MySQLdb 等常规 Python 依赖；数据库通过网络连接。

## 运行方法

1. 打开单文件，在顶部 `DB_CONFIG` 填写真实数据库连接。五个策略共用这套配置；不要将真实值提交到 GitHub。
2. 将完整代码粘贴到聚宽 Notebook 单元格执行即可，无需上传另外五个策略文件。
3. 也可以只上传这一份文件，然后执行：

   ```python
   %run -i 策略批量采集_数据库版.py
   ```

   `-i` 沿用 Notebook 中提供的聚宽 API。入口也会从 `jqdata` 和内置命名空间读取平台接口。
4. 查看每个策略完成后的结果和末尾汇总；`batch_summary` 保存名称、状态、实际新增条数、耗时、脱敏错误信息。

本机 `original/策略批量采集_数据库版.py` 已同步完整实现，并保留原有私有数据库连接，位于 Git 仓库之外。GitHub 只发布占位配置版本。采集脚本需在聚宽研究环境运行，Linux 网页后端继续读取数据库；本次改动无需重新部署网页。

## 顶部集中配置

日常调整只需要查看文件开头的配置区：

| 配置 | 用途 |
| --- | --- |
| `DB_CONFIG` | 五个策略共用的数据库地址、端口、库名及凭据 |
| `DB_OPTIONS` | 连接超时、连接重试次数/间隔、连接池回收时间 |
| `STRATEGY_CONFIG` | 按策略配置起止日期、计算参数、分页大小、ETF 名单等 |
| `STRATEGY_ORDER` | 执行哪些策略以及执行顺序 |
| `STRATEGY_OPTIONS` | 可选的 `run()` 参数覆盖，通常保持 `{}` |
| `PREVIEW_ROWS` | 每个策略在控制台预览多少条新增数据，默认 5；0 为不预览 |

`STRATEGY_CONFIG` 的默认值保持原采集口径：

- 行业动量：`start_date='2025-01-01'`、`industry_type='sw_l2'`、`retention_trade_days=180`。
- 抱团拥挤度：`start_date='2020-01-01'`、`top_pct=0.05`。
- 微盘温度计：`start_date='2021-01-01'`、`micro_num=1000`、`sample_step=5`、`batch_size=1000`。
- ETF 份额：`start_date=None`、`initial_trade_days=300`、`window_size=120`，`funds` 保存两组跟踪名单。`lookback_days` 兼容原接口，在只新增模式下不回查覆盖。
- 净利润断层：自动筛选最新已结束季度，`page_size=1000`。

各策略 `end_date=None` 均表示**每次运行时**计算北京时间当天，不在导入时固定日期。需要修改参数时，例如：

```python
STRATEGY_CONFIG['行业动量']['industry_type'] = 'sw_l2'
STRATEGY_CONFIG['净利润断层']['page_size'] = 500
batch_summary = run_all()
```

每次调用都会读取一份新的策略配置快照，修改配置后重跑即可生效。调用 `run_all(options=...)` 时，这次传入的选项替代 `STRATEGY_OPTIONS`；其中 `run()` 参数优先于分组默认配置。分页/窗口等内部参数请直接修改 `STRATEGY_CONFIG`，不要作为 `run()` 参数传入。`skip_existing=True` 固定开启，不能通过配置关闭。

连接重试仅用于建立连接，默认最多 5 次、间隔 10 秒；不会自动重放写入事务。各策略独立创建和释放连接，公共会话管理只负责异常回滚与关闭，提交时点仍由对应策略决定。不同用途的数值转换保留原精度，例如微盘指标使用 Decimal，未强制统一成浮点数。

## 执行顺序与数据规则

默认顺序为：**行业动量 → 抱团拥挤度 → 微盘温度计 → ETF份额 → 净利润断层**。同一时间只执行一个策略；每个策略拥有独立命名空间，避免 `run`、`Base`、日期参数和其他同名对象相互覆盖。

批量入口固定传入 `skip_existing=True`，只写入业务主键尚不存在的数据，不再覆盖最新一天或 ETF 回查窗口。已有行即使源数据发生变化也保留原值。

| 策略 | 批量入口的采集、清理规则 |
| --- | --- |
| 行业动量 | 先清理整张表 180 个交易日前的数据，再从该分类最新入库日之后采集；已有日期不重算 |
| 抱团拥挤度 | 从当前 TOP_PCT 最新入库日之后采集，保留完整历史 |
| 微盘温度计 | 保留 2021-01-01 起、每 5 个交易日采样；以已保存最新一期为基准继续，不改变采样间隔；保留历史 |
| ETF份额 | 首次最近 300 个交易日；每只基金从自己的最新入库日之后续传，不再回查或覆盖最近 5 日；保留历史 |
| 净利润断层 | 扫描最新已结束季度中尚未入库的股票；按“报告期＋股票代码”只新增，已入库股票保留首次快照，不覆盖、不删除 |

控制台中的条数是实际新增业务记录数；没有新增数据会输出“无新增数据（已有记录跳过，或本次尚无可入库数据）”。唯一键仍用于兜底；如果其他独立任务并发抢先写入导致冲突，该事务回滚后报告失败，不通过删除旧记录解决冲突。

净利润断层的市值、PE、PB、信号日期及公告信息保留首次入库时的值，不随以后运行刷新。其 `earnings_gap_run` 运行元数据仅在扫描截止日、累计股票数等内容变化时更新，重复运行且内容不变时也不写入；汇总中的新增条数只统计股票明细。页面的扫描截止日不代表每只股票的估值日期，应以股票自身的 `valuation_date` 为准；“命中数”表示该季度累计保留数量，不是当次重新筛选的数量。

行业动量、抱团拥挤度和微盘温度计在只新增模式下，北京时间 16:00 前不写当天日数据，避免盘中快照被永久保留。净利润断层沿用已有完整交易日规则；ETF 以数据源实际发布为准。历史已写入的不完整值或源后续修订不会自动纠正，更早缺口也不会因为从最新日期续传而自动补齐。

独立策略的 `run()` 为兼容原用法，默认仍是原先的覆盖刷新模式；如需单独运行也遵循只新增规则，显式调用 `run(skip_existing=True)`。常规任务使用模块化批量入口即可，不要再同时运行旧版单策略脚本。批量入口不允许通过参数关闭 `skip_existing`。

## 控制台结果与失败处理

入口不生成日志目录或日志文件，不显示各模块逐日、逐窗口的过程输出。每个策略完成后显示名称、成功/失败、实际新增条数和耗时，并预览最后 5 条新增数据的关键字段；没有新增数据时明确提示。字段名和单位沿用各策略：ETF `shares` 为份，温度计 `score` 为原始 0–1 分值。设置 `PREVIEW_ROWS = 0` 可关闭数据预览，只看汇总。

```text
【行业动量】成功：新增 124 条，耗时 3.10 秒。
本次新增结果（最后 5 条，字段单位沿用策略）：
...
【净利润断层】成功：新增 0 条，耗时 2.20 秒。
无新增数据；已有记录跳过，或数据源尚无可入库数据。

采集结果汇总
策略 | 结果 | 新增条数 | 耗时（秒）
行业动量 | SUCCESS | 124 | 3.10
...
净利润断层 | SUCCESS | 0 | 2.20
成功 5，失败 0。
```

- 长时间首次采集时，策略完成前没有过程输出，Notebook 仍会显示正在执行。
- 普通异常在控制台展示脱敏后的类型和简要原因，然后继续后续策略；失败策略新增条数标为“未完成”，不会误报为 0。最后默认抛出 `BatchRunError`，其 `summary` 属性保留结果。
- 各策略独立提交事务，**不会整个批次一起回滚**。失败前已成功入库的数据、已完成的过期清理保留，修复后只补新增数据。
- Notebook 中断会停止整个批次，不再执行后续策略。
- 使用内存锁阻止同一 Notebook 内核重叠执行，不读取或创建锁文件。不同 Notebook 内核或研究容器之间不共享此锁，请勿同时采集同一批数据；数据库唯一键继续约束重复记录。
- 网页服务的 `log/` 日志功能不受影响；独立策略直接运行时仍保留原有输出方式。需要本页的安静输出和只新增规则，请统一使用此入口。

## 只运行部分策略或调整参数

可修改入口顶部的 `STRATEGY_ORDER`，仅保留需要的策略，顺序就是调用顺序。例如只执行净利润断层：

```python
STRATEGY_ORDER = ['净利润断层']
```

已通过 `%run -i` 加载入口后，也可以在 Notebook 中调用：

```python
# 只重跑两个策略，按给出的顺序串行执行
batch_summary = run_all(strategy_names=['ETF份额', '净利润断层'])

# 展示汇总，不预览新增数据；有失败时不抛出批次异常，供手动检查
batch_summary = run_all(preview_rows=0, raise_on_failure=False)

# 只采集沪深300 ETF；run() 参数通过策略名称传入
batch_summary = run_all(
    strategy_names=['ETF份额'],
    options={'ETF份额': {'groups': ['hs300']}},
)
```

默认 `STRATEGY_OPTIONS = {}` 保持各策略原参数。不要随意改变微盘温度计起始日期、数量或采样步长，这些参数会生成不同序列，同日期不同序列不属于重复记录。

## 维护方式

完整策略代码直接位于批量文件内的 `_momentum_strategy`、`_crowding_strategy`、`_microcap_strategy`、`_etf_strategy`、`_earnings_strategy` 五个函数中，由 `STRATEGIES` 注册并按 `STRATEGY_ORDER` 调用。后续发布只需更新这一份批量文件。

仓库仍保留独立采集脚本供单独使用；它们不是批量文件的运行依赖。修改业务算法时，需要同步独立脚本和批量文件内对应策略；公共连接/会话工具只维护一份。离线测试检查核心计算、选股规则和表结构与独立脚本一致，并验证配置生效、连接重试、会话回滚关闭、无 `__file__` 的 Notebook 执行、无外部策略文件、串行顺序和只新增规则。真实行情权限及 MySQL 连通性仍需在聚宽验证。
