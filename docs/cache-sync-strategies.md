# 缓存同步策略与历史修复

## 日常按分类追加

以下四个模块不再每次下载远端全部主键和 `updated_at` 清单：

| 模块 | 独立水位 | 默认采集行为及源码依据 |
| --- | --- | --- |
| 行业动量 `industry-momentum` | `industry_type` | `collectors/行业动量计算_数据库版.py` 的 `run/save_day`：按分类最新日之后新增，每日/分类事务提交；`cleanup_old_data` 清理所有分类过期数据，保留180个交易日。 |
| 抱团拥挤度 `market-crowding` | `top_pct` | `collectors/抱团拥挤度_数据库版.py` 的 `run/save_day`：默认 `incremental=True, skip_existing=True`，按口径最新日之后新增；保留完整历史。 |
| ETF份额 `etf-shares` | `fund_code` | `collectors/ETF份额_数据库版.py` 的 `run/save_window`：默认按每基金最新日之后新增，每基金窗口事务；已有行及其 `previous_trade_date` 不改写。 |
| 微盘新高新低 `microcap-breadth` | `series_id` | `collectors/微盘新高新低数量统计_数据库版.py` 的 `run/save_day`：按序列最新日之后新增，每日事务，失败即停止，不自动跨过缺失日。 |

批量采集脚本的对应实现使用相同语义。ETF份额允许其他基金在某基金失败后继续，故必须保留每基金独立水位，不能使用全表最大日期。

后端每次读取每分类最早/最晚日期，只下载成功水位之后的数据；首次出现的分类读取其全部现存数据。分类最早日期前的本地旧记录会清理；分类消失（包括源表变空）会移除其本地数据和水位。源边界回退会重建该分类。整个源读取使用同一个 MySQL repeatable-read 事务。

水位存放在不可变 SQLite 快照内，与数据同事务提交；失败不发布新快照，下次仍从旧成功水位重试。没有新日期或边界变化时，复用原快照，不复制 SQLite 文件。首次运行或旧快照缺少新版游标时，先完整建立基线，不能直接把旧本地最大日期当成可信水位。首次迁移仍可能较慢。

## 必须保留其他同步方式的模块

| 模块 | 保留策略 | 原因与源码入口 |
| --- | --- | --- |
| 市场情绪 | 主键/时间戳对账 | `市场情绪跟踪_数据库版.py:run` 默认填补近三年任意历史缺口，并删除过期日期；仅最大日期会漏掉回填。 |
| 微盘温度计 | 主键/时间戳及修复标记对账 | `微盘温度计_数据库版.py:collect_daily/repair_daily_derived/mark_daily_pending` 补历史后会修改后续分位、指数与计数。 |
| ETF动量热度 | 主键/时间戳对账 | `ETF动量热度_数据库版.py:run/save_rows` 回填历史缺口；规则迁移或 `repair_missing` 可修复旧空得分；候选池可变，180交易日清理。 |
| 短线选股 | 主键/时间戳对账 | `短线选股_数据库版.py:run/save_day` 可替换同日旧规则结果，补齐保留窗口缺日，保留3交易日。 |
| 净利润断层 | 季度头和股票成员对账 | `净利润断层_数据库版.py:save_results` 在同季度持续新增股票并更新元数据；显式修复可替换整季。 |
| 高股息、高增长 | 完整最新快照替换 | 对应采集脚本的 `save_latest/_replace_latest_snapshot` 维护可变最新名单，不是日期追加序列。 |
| 个股机构持仓 | 事务变更日志增量 | `backend/app/core/ownership_sync.py` 保留 generation/revision、删除标记和原子游标；无日志的旧采集器仍回退对账，不能改为日期水位。 |

这些模块虽然部分采集函数也叫“只新增”，仍有历史修复或名单变更，不能一律按最大日期同步。

## 人工修复历史：完整重建

四个日期水位模块的日常同步**不检查保留范围内已有日期的修改、补洞或中间删除**。例如同一行业日期补入遗漏行业、修改历史份额、手工修复指标后，应执行该模块完整同步。首次基线只能复制源数据库现状，不能判断源本身是否漏采；行业日快照也没有独立完整性标记。

在页面“数据同步”中选择受影响模块，将同步方式改为“完整重新同步（修复历史）”后执行。默认仍为日常同步；完整重建耗时更长，成功启动后会恢复默认选择，避免下次误做完整重建。

也可在已有运行后端的地址上调用（示例地址按部署替换）：

```bash
# 普通增量同步
curl -X POST http://127.0.0.1:8000/api/v1/cache/refresh \
  -H 'Content-Type: application/json' \
  -d '{"module":"industry-momentum"}'

# 历史修复后，完整重建该模块的本地快照
curl -X POST http://127.0.0.1:8000/api/v1/cache/refresh \
  -H 'Content-Type: application/json' \
  -d '{"module":"industry-momentum","full":true}'

curl http://127.0.0.1:8000/api/v1/cache/status
```

`202` 表示任务已接受，不表示完成；用状态接口确认模块成功且无错误。已有任务运行时返回 `409`。省略 `module` 会同步全部模块；完整修复建议只指定受影响模块。后端内部等价入口是 `cache.refresh(module, full=True)`；不要只调用 `copy_module`，它不负责发布状态。

完整重建只重新读取源数据库，不会重算采集结果，不会恢复源已过期删除的数据，不修改生产源表。人工修复源数据与后端缓存重建是两个独立步骤。

## 性能边界

分类聚合输出是一类一行，不再传输每条历史记录的主键/时间戳；这不等于保证数据库内部零扫描。源表 `(分类字段, trade_date)` 索引可帮助 MIN/MAX 分组查询。拥挤度、ETF份额、微盘新高新低的主键已以分类字段和日期开头；行业动量源主键以日期开头，现有采集表没有分类优先索引，聚合可能仍扫描索引。

本次后端优化不擅自修改生产 MySQL 索引。若需进一步优化，数据库维护者应先检查现有索引和执行计划，再评估添加 `(industry_type, trade_date)` 索引。测试中的 SQL 次数、传输行数和是否复制文件是合成测试结果，不代表生产网络耗时承诺。

合成回归测试（`backend/tests/test_cache_append.py`，SQLite 模拟源）：

| 同一分类已有历史 | 无新增远端 SQL | 返回内容 | 本地文件复制/历史表扫描 |
| --- | --- | --- | --- |
| 1行 | 1次 | 1行分类最早/最晚日期 | 无 |
| 2501行 | 1次 | 1行分类最早/最晚日期 | 无 |

本地总行数保存在与数据同事务提交的版本标记中，无变化时不执行历史表 `COUNT`。这些测试验证的是 SQL 形态、请求次数和本地行为；未测量生产 MySQL 的查询执行计划、网络延迟或真实加速倍数。
