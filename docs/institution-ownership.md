# 个股机构持仓与社保新进

## 采集与运行

在聚宽研究环境运行 `collectors/个股机构持仓_数据库版.py`，或新版 `策略批量采集_数据库版.py` 的“个股机构持仓”。两个入口均为独立单文件，不读取外部配置。顶部 `DB_CONFIG` 填写数据库配置，GitHub 版本仅有占位值。

默认首次采集最近五年，并额外读取第一个季度的前一季度，用于社保新进比较。初次采集可能耗时较长，控制台展示报告期及分页进度。股票范围为运行日上市的 A 股；已有历史保留，不删除退市股票历史。增量披露代码须匹配当前 A 股清单或已有股票档案，不在范围内的代码（例如行情接口不支持的 `K0470.XSHG`）会显示忽略提示，不加入持仓复查。基金持仓的六位代码按股票清单转换，带交易所后缀的代码须完整匹配。

后续运行先检查公募持仓、十大流通股东、股东户数三张源表的最大记录 ID，以及最新披露日期/ID（共六次只返回一行的查询）。检查标记不变时跳过股票资料、持仓复查和户数采集；分类规则升级时先修复已有 JSON，近期缺少源分类的少量记录另做每日一次的定向补查。检测到源记录变化后，按来源分别处理：

- 公募新增披露按实际 `period_end` 定位股票和报告期，只更新历史采集范围内（含最早比较季）对应季度的公募汇总。退出股票从同一基金、同一季度的旧报告及关联份额找回；不再把该基金四季所有持股合并后逐季重查。对受影响的股票和季度，重新汇总全部基金的有效报告，保留其余六类持仓和社保结果，不查询十大股东或行情。
- 十大流通股东新增披露只复查对应股票最近四个季度的十大股东和社保比较，保留已有公募汇总，不重读基金报告，也不查询用于估值的期末行情。
- 股东户数新增披露只更新对应股票的户数。没有变化的其他来源保留已有结果。

同一主键的内容不变时不重复更新。首次采集、采集范围参数变化或手动完整刷新仍使用完整路径；其中户数继续读取最近成功采集日前 30 天以来披露或统计的数据。需要全范围核对原地更正时可用 `run(full_refresh=True)`；批量入口设置 `STRATEGY_OPTIONS = {'个股机构持仓': {'full_refresh': True}}`。日常增量及本次升级不需要完整刷新。没有 180 个交易日清理规则。

v8 沿用已有 `ownership_disclosure_probe` 检查记录和持仓数据，不重建基线，也不新增分基金明细表。尚未建立检查记录的旧库按原断点执行完整路径，成功后建立检查记录。检查记录只在整次采集成功后推进，失败仍可重试。手动 `full_refresh=True` 绕过检查。该检查依赖源表新增 ID 或最新披露标识的变化，同 ID、同披露日期的持股数量等原地更正不会单独触发复查；缺少源分类的记录沿用 v7 的限量补查；仅基金主代码映射、股票名称或行业变化也不会触发。若需要覆盖这些变化，使用手动完整刷新。披露高峰期实际变化股票和持仓仍可能较多，优化不保证每次采集都能在固定时间内完成。

每个报告期以事务提交，失败的报告期回滚，已完成的报告期保留。未完成采集需重跑；新的报告期和户数水位只有完成相应查询和写入后才保存。`end_date=None` 表示北京时间当天；未来披露日期排除，股东户数未知披露日期保留并标注。采集时采用当时可取得的基金主代码映射，不能用于严格历史时点回测。

首次使用需要 MySQL 5.7.8+ 原生 JSON 支持，推荐 MySQL 8；采集账号需建表及写入权限。表由脚本自动创建，网页账号只需读取。无需安装新的项目依赖。实际聚宽大规模采集、接口额度及数据覆盖需在您的研究账号中验证。

## 研究环境内存控制

采集改为逐页迭代，不再把整季原始记录或全市场历史 JSON 一次装入内存。默认配置：

```python
STRATEGY_CONFIG['个股机构持仓']['page_size'] = 1000
STRATEGY_CONFIG['个股机构持仓']['stock_batch_size'] = 50
```

`page_size` 控制聚宽每页返回行数；`stock_batch_size` 控制同批股票数（1—300）。内存仍紧张时可分别降为 500 和 20。减小批次会增加接口请求和数据库查询次数，采集可能更慢；不会缩短历史范围或改变筛选条件。

公募先以少量字段分页确定每个基金的完整报告版本，再按股票批次读取持仓，避免 A/C 去重或新版报告缺失某股时误用旧持仓。关联基金和报告版本的索引查询每批 300 个标识，与默认每批 50 只股票的持仓计算分开。持仓明细在源 SQL 中按选定报告的原始基金代码、披露日期、报告类型精确过滤；每块最多 8,000 份报告、128 组条件，超出后拆分查询，不再先下载全部旧版本再由 Python 丢弃。分页仍持续到空结果，防止平台返回上限造成漏数。股东户数和社保比较同样分批，数据库写入后 flush 并释放该批 ORM 对象。整季完成才提交事务和断点；中途异常仍整季回滚，不能把 flush 当作已提交。

内存仍需保留股票/基金标识映射及本次变更记录的简短键值，返回结果不包含原始持仓或历史 JSON。无需清空数据库、重新建表或重建网页。若旧脚本已因内存不足失败，先重启聚宽内核释放旧对象，再运行新版独立脚本或新版批量脚本，已有不变记录不会重复写入。

## 存储和缓存

- `ownership_stock`：股票代码、名称、当前申万二级行业。
- `ownership_report`：股票代码＋报告期为联合主键，JSON `payload` 保存七类汇总、流通股东明细、社保新进结果、数据口径。数量为股、比例为百分数；只有公募保留直接披露的市值，金额为元。
- `ownership_holders`：股票代码＋统计日期为联合主键，披露日期及 JSON 户数字段；总户数和 A/B/H 股户数分开。
- `ownership_checkpoint`：采集断点，仅采集端使用。

前三张表通过事务变更序号增量同步到项目本地 SQLite，页面不直接访问公网数据库。在“数据同步”选择“个股机构持仓”，或等待北京时间 07:00 自动同步。首次新增模块会改变当前缓存结构标识，因此其他模块也可能需要重新建立本地快照。

## 本地同步加速

新版采集器自动新增 `ownership_sync_head` 和 `ownership_change` 两张轻量表。每个写入事务使用单调变更序号，实际数据、变更键和删除标记一起提交或回滚；同一主键只保留最新变更状态，不保存重复的历史 JSON。

本地 SQLite 内的 `ownership_cache_cursor` 保存源库代次和同步序号。首次建立基线仍需下载全部数据；后续只读取序号之后的变更键及相应记录，包括历史补录、更正、删除。源版本没变化时直接保留原文件，不扫描业务历史、不复制快照，页面数据更新时间也不会无意义地改变。日志会显示 `Cache ownership unchanged`；有变化则显示 `Cache ownership journal` 和下载条数。

启用顺序：部署并重启新版后端 → 在聚宽运行新版独立/批量采集脚本 → 页面同步本模块。已有旧缓存会在启用变更记录后建立一次完整基线；后续走快速增量。数据库没有新元数据表时自动兼容旧主键/更新时间扫描。无需手工删表或清空缓存。

启用后所有写入必须使用新版采集器，不能混用旧脚本；人工 SQL 修改或删除不会自动生成变更记录。此类操作后应强制完整同步：

```bash
backend/.venv/bin/python scripts/refresh_cache.py --module institution-ownership --full
```

Windows 将解释器路径替换为 `backend\.venv\Scripts\python.exe`。不要手工清理变更键或删除标记；其容量随不同记录主键数量增长，而不是随每日运行次数增长。完整同步仍可用于源库恢复、人工修复后的重新核对。有变化时仍复制本地快照再合并，保证页面查询不被打断；此次优化不消除首次下载耗时及有变化时的本地复制开销。

## 统计口径

公募取 `FUND_PORTFOLIO_STOCK`。同基金同一期先选择半年报/年报等完整披露，再选择最新披露版本；利用 `FUND_MAIN_INFO.statistics_main_code` 映射去重，没有映射时保留原产品代码，不能承诺所有未知份额类别都已合并。季报与半年报/年报范围不同；统计产品数不是基金管理公司家数。

其他六类（社保、保险、券商、QFII、信托、私募）使用 `STK_SHAREHOLDER_FLOATING_TOP10` 的定期报告（306019）、流通 A 股（308007），汇总直接披露的持股数量，页面单位为万股；产品／账户数另行展示。不再查询期末行情或估算市值，分类汇总的 `value_method` 为 `reported_shares`。无披露记录不补零，不能解释为清仓。聚源 `LC_StockHoldingSt` 当前账号数据止于 2019 年，未使用。

历史 JSON 已保存披露股数，升级页面与后端即可按股数展示，无需重新采集、清空缓存或全量同步。接口忽略旧的非公募估值字段；新版采集器在正常处理报告时清理这些旧字段，不为此单独扫描、重写所有历史。公募继续显示基金报告直接披露的市值汇总。

分类 ID：QFII 307007；社保 307004；券商 307002/307015/307022；保险 307006/307014/307023；信托 307009/307016/307025；私募 307028。保留原细分类别，其他机构不按名称猜测为私募。

## 社保新进

默认最新已结束季度，不自动退回较旧的已披露季度。仅当本期及紧邻上一季度均有完整 1—10 名名单、股东名称和分类齐全时判定；不跨越缺失季度比较。以股东 ID 或规范化名称匹配，减少更名或 ID 变化误报；未匹配到的账户仍可能存在源数据标识变更，应结合公告核查。

- 股票首次出现社保持仓：本期有新进入名单的社保组合，上期完整名单无社保。
- 新增社保组合：本期出现上期所有股东中不存在的社保组合，原来已有社保也可入选。仅分类变化不算新进。

“新进”只代表进入十大流通股东名单，不代表首次买入。季度披露未完成期间，可比较样本会逐步增加。界面展示可比较数、无法判定数、组合名称、持股数量和披露持股比例，并支持跳转个股。首次出现社保和新增社保组合按新进组合合计持股数降序；社保组合加仓按两季合计持股数的增加量降序，均不使用市值排序。

## 发布使用

按照 README 的 Linux 发布步骤执行 `bash deploy.sh`，确保后端重启、前端重建；Windows 停止旧进程后重新运行 `start.cmd`。先在聚宽完成采集，再同步本模块。进入总览“个股机构持仓”，选择“个股查询”或“社保新进”。

## 首次全量同步断点续传

机构持仓首次建缓存、升级基线及强制完整同步，在源库有 `ownership_sync_head` 和 `ownership_change` 时支持续传。报告每页最多500条，股票基本信息和股东人数每页最多2000条；数据和最后成功的主键一起提交至 `log/cache/<指纹>/ownership-baseline.partial`；文件内 `ownership_baseline_checkpoint` 记录源版本、表序号、主键和已保存行数。它只属于未发布缓存，不增加 MySQL 表，正式快照仍为三张业务表加同步游标。

网络重试、手动重新同步或服务重启后的下一次同步，会跳过已成功落盘的页。未完整收到或未提交的那一页重新下载。阶段进度可显示已保存的断点行数；日志搜索 `Cache ownership baseline resume` 查看 `saved_rows`。服务启动仍不自动同步，需手动触发或等下一次定时任务。

不同尝试可能对应不同的源库快照，因此最后会在一致事务视图下重放初始版本之后的变更记录，修复已下载部分发生的修改、删除和主键较早的新插入，成功后才发布。补差失败也保留已经下载的基线，但补差事务本身会回滚并重试。源库代次变化或版本回退时，旧断点不能复用，需要重新建立基线。全部写入必须经过新版聚宽采集脚本维护变更记录。

未完成文件不供页面读取、不按24小时旧快照规则清理。最终发布需复制出正式文件，因此完成时需要容纳续传文件和正式文件的磁盘空间；成功发布后自动删除对应续传文件。发布或复制失败仍保留断点。已经成功发布的旧缓存不受中断影响。

没有变更记录的旧库继续使用原完整事务同步，不提供跨连接续传，以免遗漏源数据变更；先运行新版采集脚本可启用。升级前旧版本失败时已删除的数据无法恢复，升级后新下载并提交的页才可续传。其他模块及机构持仓普通增量同步沿用原有失败重试机制。

## 公网传输与本地写入优化

`CACHE_OWNERSHIP_COMPRESSION=true` 默认开启：MySQL 查询结果中的 JSON 使用 `COMPRESS(CAST(... AS CHAR CHARACTER SET utf8mb4))` 压缩，项目接收后检查解压长度并还原为原 JSON 文本写入 SQLite。不修改源表内容，不改变查询条件、主键分页、增量水位或断点格式，也不需要重新采集。正式缓存仍是普通 JSON，可以正常读取。

仅在实际下载机构持仓数据时探测压缩支持；源版本未变化时不探测或下载。服务器没有压缩支持时回退为文本搬运；网络断开走正常重试，损坏的数据不会发布。压缩减少网络流量，但会消耗少量数据库 CPU；若数据库 CPU 紧张，可在所用配置文件中设置 `CACHE_OWNERSHIP_COMPRESSION=false` 并重启后端。Linux 使用 `config/app.config`，Windows 默认使用 `backend/.env`。

全量续传复用一个 SQLite 写连接，避免每页重新打开文件；仍按页提交，保持数据与断点原子性，不关闭事务安全设置。小记录页从500条扩大到2000条，减少约四分之三的数据页请求（不足整页、结束探测和补差另计），大型持仓报告保留500条以控制单次传输量和内存。

本机对当前数据库的只读500条报告样本测得 JSON 约1,041,177字节，压缩后451,198字节，减少56.7%；单次读取约3.05秒与2.75秒。该采样不是 Linux 服务器的端到端同步基准，不能推算固定提速比例。分页 EXPLAIN 使用 PRIMARY 范围扫描；不要仅凭同步慢重复创建主键组合索引。实际数据页大小也不等于网络传输字节数。

参考：[MySQL COMPRESS 官方格式说明](https://dev.mysql.com/doc/refman/8.0/en/encryption-functions.html#function_compress)。

定向复查沿用已成功建立的 `ownership_disclosure_probe`，无需再次全量建立基线。若上次采集未完整成功、尚无检查记录，仍按原断点执行首次复查。控制台打印触发来源、各源增量记录数及影响股票数，并分别显示公募分期更新、十大股东四季复查及股东户数更新范围。需要更新公募的季度，先按受影响股票查询关联基金，再查询这些基金及关联份额的报告版本；不进行无股票或基金范围限制的全市场季度扫描。关联份额仍一起核对，以保持 A/C 去重及退出持仓识别正确。


### 报告索引去重与可见进度

报告索引去重版 v4 在源查询中按基金代码、披露日期、报告类型分组，使用每组最小 ID 分页；查关联基金和新旧报告股票也在查询端去重。分页持续到空结果，避免平台分页上限导致遗漏。它减少返回研究环境的重复行，不保证源数据库执行聚合没有扫描成本；实际持仓数量和金额仍从限定股票的明细计算。

批量脚本会静默普通策略 print；本模块范围提示改为独立可见通道，会保留版本号、首次/定向模式、受影响股票数及相关基金代码数。进度中的“去重索引”与“读取持仓明细”含义不同。关闭进度条仍会显示简短范围提示。无需删除已有数据库记录或采集检查记录。聚宽研究环境对分组查询的实际支持及耗时仍需上线运行验证，查询失败不会自动退回全市场明细扫描。

### 未知标的错误修复（股票范围校验版 v5）

若旧版因 `ParamsError: 找不到标的K0470.XSHG` 失败，替换聚宽中的整份批量或独立采集脚本后重跑即可，沿用已有数据、断点和披露检查记录，无需清表或开启完整刷新。批量脚本仅重跑本模块时，将末尾调用改为 `batch_summary = run_all(['个股机构持仓'])`；日常全策略采集恢复 `run_all()`。当前版本启动时会显示“分源分期增量版 v8”。

### 持仓与股东户数分开增量（v6）

沿用 v5 的股票范围校验和既有披露检查记录，不重建基线，也不需要清表或完整刷新。仅户数变化时不加载基金主份额映射，并保留已有股票资料，新出现的股票仍补建名称与行业档案。无任何源标记变化时仍只做六次源检查并跳过后续采集。

日志依次显示“触发来源（公募持仓/十大流通股东/股东户数）”“增量源记录数及影响股票数”“持仓复查范围”“股东户数更新范围”。首次建立基线、手动完整刷新、采集范围参数变化会另行明确说明。股票总数没增加，不代表同一股票没有新披露；源表新增或新可见记录，也不保证最终业务结果有变化，因此入库条数仍可能为零。

所有需要执行的阶段成功后，才更新整体披露检查记录。中途失败不推进检查记录，已提交结果保留；重跑继续检查未完成的更新。测试覆盖仅户数变化时除六次披露检查外，不读取持仓明细或基金资料、仅持仓变化不重读户数、两种变化同时出现、失败重跑及未知标的跳过。


### 缺失分类补全与已有数据修复（v7）

聚宽可能先发布十大流通股东的名称、股数，再补 `shareholder_class_id`。现期有效分类优先；缺失时仅识别明确的全国社保/社会保障基金编号组合，以及明确的普通证券投资基金名称，或使用同一股票过去报告中同名/同 ID 且没有冲突的原始分类。不会按“证券/保险/信托”等泛关键词猜测，也不会把养老基金、私募产品当作社保。名称比较统一空格、常见横线及全半角字符，保留组合编号。推断结果不能作为新的原始证据，不能从未来报告回填过去。

成员保留 `raw_class_id`、`class_source` 和社保三态 `is_social`（仅缺分类或补分类成员增加）；`float_list_complete` 检查十个名次及姓名，`float_complete` 检查全部机构分类，`social_complete` 单独检查能否可靠判断每名股东是否社保。能识别的持仓仍展示；分类不完整的合计标注 `complete=false`，页面提示“仅统计已识别持仓”。名单或社保身份不完整时不参与新进/加仓比较，不把未知当作零。公募汇总继续使用原来的独立披露来源。

分类修复升级后，即使没有新增披露，也会先按股票分批修复数据库中既有的不完整名单，重算相邻季度社保比较；保留股数、比例和独立公募汇总，清理非公募估值字段。使用 `ownership_disclosure_probe` 的 `classify-v1` 保存修复游标，事务提交与游标同步，中断后继续；已完成后不重复扫描。本次改用股数不重置该游标。仅变化报告更新 `updated_at` 与同步变更记录，因此页面可增量同步，无需重采全市场、清表或强制完整同步。

为了发现聚宽同记录原地补分类，每天额外轮转检查近期四季 `classification_pending=true` 的股票，最多 50 只（`stock_batch_size` 更小时按该值）。只查询限定股票的十大流通股东，不查询基金报告、行情或股东户数。仅当披露日、名次、名称、股数、比例与已存快照一致时补原始分类；新版本或数量变化由原披露流程处理。数据未变不写业务记录、不增加同步版本。`classify-retry` 保存独立检查日期及游标；失败不推进。同日重复运行不重复补查。无法可靠分类的记录仍保留未知，不能保证数据源未提供的信息一定可推断。

项目环境也可使用 `scripts/repair_ownership_classification.py` 先预览、再用 `--apply` 修复已有 JSON，`--code 002281.XSHE` 可限定股票。该工具不调用聚宽，不触发新行情/持仓采集；需要数据源补分类时在聚宽运行新版采集器。工具及采集器均维护原有同步变更日志。

页面比例列改称“披露持股比例”，直接沿用源字段，不再将其无条件称为占流通股比例；若需要严格流通股分母，应另采可靠流通股本计算。

### 公募按报告期增量与源查询过滤（v8）

公募新增披露不再触发所有关联股票的四季全项复查。例如只有某基金三季报新增时，先找该基金三季报新旧版本涉及的股票，再仅重算这些股票三季度的公募合计；其他季度和社保结果保持原值。若历史采集范围内的旧季度新增披露，则更新对应旧季度。重算时仍包括其他未变化基金的有效持仓，不能仅把新披露基金的合计覆盖股票公募总额。

十大流通股东新增披露仍按原约定复查该股票最近四季，但只更新该来源及社保比较；公募汇总保持原值。两种来源同次变化时，分别处理后合并到同一份股票季度 JSON。股东户数及 v7 的分类修复、每日限量补查继续独立执行。

替换聚宽中的整份独立或批量脚本即可，已有数据、分类修复游标及披露检查记录继续使用；不要为本次升级设置 `full_refresh=True` 或删除检查记录。每个季度成功提交后保留，失败季度回滚；整体披露检查记录只有全部阶段成功才推进，失败后可以重跑，内容不变不会重复写入或生成同步变更。此次没有新建分基金持仓表，也不需要重建网页本地缓存。

索引批次扩大和有效报告条件下推可减少请求往返及无效明细传输；真实耗时、源聚合执行成本和接口限额仍需在聚宽账号中验证，不承诺固定提速比例。
