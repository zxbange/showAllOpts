# 数据结构迁移与发布边界（高股息试点）

本次仅整理现有高股息迁移逻辑，不新增生产表、字段、版本记录表或额外数据迁移。采集程序仍使用原数据库配置；未在部署或应用启动时增加 DDL 步骤。

## 迁移规则

后端 `app/repositories/dividend_schema.py` 根据实际数据库列信息生成确定性迁移计划，每项迁移有固定标识：

| 标识 | 旧结构条件 | 原有兼容动作 |
| --- | --- | --- |
| dividend-001-rule-version-capacity | rule_version 可确认长度小于 64 | 扩至 VARCHAR(64)，不缩短更宽的列 |
| dividend-002-per-share | 缺少 dividend_per_share | 增加可空 NUMERIC(24,8) |
| dividend-003-fiscal-year | 缺少 dividend_fiscal_year | 增加可空 INTEGER |
| dividend-004-cash-nullability | dividend_cash_1y 不允许 NULL | 调整为可空 NUMERIC(28,6) |

MySQL 5.7 和 8.4 的 DDL 不属于后续业务写入事务。每一步执行前查验实际列结构，执行后重新查验；已经满足的 revision 不重复执行。不能仅根据某条 DDL 返回成功或客户端连接中断声称迁移成功。发生部分迁移、权限不足、锁等待或断线时，保持原有待发布结果，重试前从数据库当前结构重新生成计划。没有引入自动回退或缩列。

这不是跨进程数据库迁移锁。现有应用执行锁继续保护本模块内部发布，但外部聚宽作业或管理员 DDL 仍可能竞争；出现错误停止并保留候选结果，不猜测其他写入者是否已经提交。历史 SQLite 缓存不自动执行 MySQL ALTER，缺少必需列时仍拒绝在旧结构发布，由现有缓存机制重建。

## 验证和风险控制

- 业务快照元数据、银行及非银行名单在迁移后的单独事务中一起替换；迁移本身不修改任何业务行。
- 旧规则数据不转义为新版股息率，不猜字段，不清理历史档案。
- 保留现有采集进度、数据库诊断及发布重放规则。
- MySQL CI 对应 5.7 / 8.4 隔离空测试库；验证真实旧结构迁移前后业务行、DECIMAL、JSON 及第二次执行不再发 ALTER。普通离线测试模拟中途 DDL 中断及后置核验失败。

## 后续迁移顺序

1. 先将高股息、奶牛股的读取/写入映射和事务契约明确为类型化数据层接口，保留业务校验与发布恢复服务。
2. 梳理本地状态库的创建/兼容 DDL，例如估值标尺 members 迁移、ETF 和市场情绪持久队列；为每个 SQLite 文件建立独立兼容版本和回滚测试。不把缓存临时表和持久业务表混为同一种迁移。
3. 再评估其他 MySQL 写入脚本与网页的共同表结构、外部聚宽历史入口及部署流程。需要真正的新 DDL 时，独立评审锁等待、权限、旧客户端兼容性以及可恢复备份，不随普通应用启动强行变更。
4. 在明确所有写入者的一致性协议后，才考虑独立迁移命令/统一账本。当前命名 revision 是实际 schema 证据和恢复单元，不是已新增的生产数据库版本表。
