# 数据结构迁移与发布边界（高股息试点）

本次仅整理现有高股息迁移逻辑，不新增生产表、字段、版本记录表或额外数据迁移。采集程序仍使用原数据库配置；未在部署或应用启动时增加 DDL 步骤。

## 迁移规则

后端 `app/repositories/dividend_schema.py` 根据实际数据库列信息生成确定性迁移计划，每项迁移有固定标识：

| 标识 | 旧结构条件 | 原有兼容动作 |
| --- | --- | --- |
| dividend-001-rule-version-capacity | rule_version 可确认长度小于 64 | 扩至 VARCHAR(64)，不缩短更宽的列 |
| dividend-002-per-share | 缺少 dividend_per_share | 增加可空 NUMERIC(24,8) |
| dividend-003-fiscal-year | 缺少 dividend_fiscal_year | 增加可空 INTEGER |
| dividend-004-cash-nullability | dividend_cash_1y 不允许 NULL | 调整为可空 NUMERIC(28,6) |

MySQL 5.7 和 8.4 的 DDL 不属于后续业务写入事务。每一步执行前查验实际列结构，执行后重新查验；已经满足的 revision 不重复执行。不能仅根据某条 DDL 返回成功或客户端连接中断声称迁移成功。发生部分迁移、权限不足、锁等待或断线时，保持原有待发布结果，重试前从数据库当前结构重新生成计划。没有引入自动回退或缩列。

这不是跨进程数据库迁移锁。现有应用执行锁继续保护本模块内部发布，但外部聚宽作业或管理员 DDL 仍可能竞争；出现错误停止并保留候选结果，不猜测其他写入者是否已经提交。历史 SQLite 缓存不自动执行 MySQL ALTER，缺少必需列时仍拒绝在旧结构发布，由现有缓存机制重建。

## 验证和风险控制

- 业务快照元数据、银行及非银行名单在迁移后的单独事务中一起替换；迁移本身不修改任何业务行。
- 旧规则数据不转义为新版股息率，不猜字段，不清理历史档案。
- 保留现有采集进度、数据库诊断及发布重放规则。
- MySQL CI 对应 5.7 / 8.4 隔离空测试库；验证真实旧结构迁移前后业务行、DECIMAL、JSON 及第二次执行不再发 ALTER。普通离线测试模拟中途 DDL 中断及后置核验失败。

## 已实施范围与后续边界

下文描述当前代码中的四个试点：高股息 schema 和原子快照、奶牛股快照、估值/ETF/市场持久 SQLite schema。所有入口仍使用原文件与既有兼容步骤，不新增生产迁移版本表。后续针对其他 MySQL 写入脚本、外部聚宽历史入口和真实新增 DDL，应分别确认所有写入者的一致性、锁等待、权限、旧客户端兼容以及可恢复备份，再决定是否需要独立迁移命令或统一账本。

## 奶牛股数据层（第二个试点）

`app/repositories/cash_cow_snapshot.py` 保留既有 `cash_cow_snapshot` 单行三窗口 JSON 结构：创建表仍为原来的存在性检查，不增加迁移版本或字段。类型化 `SnapshotRecord` 与 `PublicationResult` 明确写入候选和实际采用结果的区别。相同已提交内容不执行第二次写入；较新的已验证外部快照仍优先，比较 JSON 内精确时间而非可能截断/舍入的 MySQL DATETIME。3/5/10 年同时替换，事务失败保留上一结果。

财务筛选规则、完整窗口核验、采集阶段日志、重试和本地发布仍由服务层负责，不能把仓储返回值直接当作网页本地缓存已成功。真实 MySQL 测试继续复用隔离测试库，验证首次写入、幂等重放、同一秒内的新旧顺序和实际更新后回滚；这不等于生产断线已复现。

ETF 的份额、价格、交易日增量写入不是单行快照，市场热度/抱团拥挤度还依赖写入意图和数据哈希以识别外部写入者。两者不能简单套用奶牛股仓储的替换或重试策略。下文已有 SQLite 队列 schema 的独立兼容入口和测试。进一步抽取业务写入元数据或发布结果接口须单独验证；任何新 DDL 单独评审。

## 持久本地状态库（第三个试点）

三个数据库文件分别拥有自己的 schema 初始化入口，不引入统一状态表，也不把持久历史视作可重建缓存：

| SQLite 文件 | 初始化入口 | 兼容 revision |
| --- | --- | --- |
| valuation-ruler/history.sqlite3 | `repositories/valuation_state_schema.py` | valuation-001-members-nullable，依据实际列的 NOT NULL 属性，事务内复制、替换旧表 |
| etf-collection/state.sqlite | `repositories/etf_state_schema.py` | etf-001-run-history，沿用原 metadata.run_history_migrated 标记，锁内二次检查后同时写入历史与标记 |
| market-collection/state.sqlite | `repositories/market_state_schema.py` | 原 CREATE IF NOT EXISTS，保留已有调度、行情来源、重试及写入检查点；不添加新的 revision 标记 |

现有数据库文件、文件权限、连接超时、SQL 表结构和业务状态字段保持不变。估值成员兼容步骤由调用者的事务上下文提交或回滚；ETF 首次回填使用 BEGIN IMMEDIATE 防止两个进程根据同一陈旧标记竞争，标记存在时仍走只读快速路径。历史回填仅迁移已有终态记录，不伪造完成时间或丢失重试范围。市场初始化只补缺失的现有表和索引，不重置已有数据。三者无新增 DDL；不宣称支持任意第三方修改的旧结构。

新增隔离 SQLite 测试覆盖 ETF 标记失败后整体回滚与重放、市场已有待更新日期及检查点兼容、估值已有空 PE、状态与二进制工作簿；原估值旧表升级中断回滚测试继续执行。

后续数据层不应为统一而统一：高股息 MySQL 写入仍需保留两组名单、规则版本和精确结果匹配的原子边界，可单独提取存储接口；ETF 增量写入、市场的发布意图/外部数据哈希不能套用单行快照。公共发布暂存、数据库提交和本地缓存刷新是独立状态，缓存刷新失败不能伪装成源数据库未提交。需要新增 schema 版本表、跨进程迁移锁或跨模块写入接口时，应先明确实际兼容需求及所有写入者，不随本次整理自动实施。

## 高股息原子数据发布边界（第四个试点）

`app/repositories/dividend_snapshot.py` 负责已经校验的高股息候选的数据库事务、存储等价判断和已固定本地快照的读取。仍使用原有 schema、MySQL 行锁及 SQLite 事务：

- 服务层先执行原始筛选完整性验证，再调用原有 schema revision 检查；任何 DDL 都在数据库快照事务之外。
- 仓储先锁定单行头部并拒绝较旧交易日，检查取消请求；读取全部现有股票，比对元数据和两组股票（按照原 DECIMAL/JSON 存储精度），仅有差异时才在一个事务内替换。先插头部再替换子行的并发保护、两次取消检查、空结果返回值和原有阶段回调保持不变。
- 服务继续拥有数据源、候选暂存、断线重放、数据库配置、脱敏阶段日志及本地缓存刷新与严格核验。仓储不会主动重试、发送通知或判断采集成功。网页查询仍使用原 `DividendRepository.latest` 单条查询读取。
- 奶牛股的完整快照校验移至无发布/缓存服务依赖的 `app/repositories/cash_cow_validation.py`，服务和缓存共用原来的校验口径，消除 cache ↔ cash_cow_import 直接反向依赖。该校验仍使用原纯筛选规则模块，不改变规则或数据。
- 真实 MySQL 隔离 CI 仍通过原服务入口测试 schema 迁移、DECIMAL/JSON 存储、幂等重放、事务回滚、提交确认丢失和缓存发布；无需新增 DDL 或实库准备步骤。

阶段完成边界：本阶段已为高股息和奶牛股建立原子发布边界，为估值、ETF 和市场持久 SQLite 库建立独立 schema 入口；没有新增生产迁移。其余核心缓存依赖（ETF 配置、系统配置与采集调度/历史导入）涉及业务编排、配置所有权、运行时数据源或其他功能的状态规则，不能仅靠迁移模块路径消除，应在独立的依赖注入或应用编排重构中逐个验证。剩余 ETF 多表增量、市场意图/哈希事务的专用写入契约仍可另行研究，但在没有共同事务/兼容需求前不要求为它们建立同一个通用仓储。
