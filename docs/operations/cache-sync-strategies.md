# 缓存同步策略与历史修复

## 各模块当前同步方式

| 模块 | 普通同步 | 无变化时 |
| --- | --- | --- |
| 行业动量、微盘新高新低、市场情绪跟踪、微盘温度计、ETF动量热度 | 先读 result_sync_head；按 result_sync_change 的变化主键读取新增/修订，应用删除标记 | 有效基线且版本不变时复用快照，不读取业务历史、不复制 SQLite |
| 抱团拥挤度 | 按 top_pct 读取日期边界，追加水位之后的数据；边界变化时处理对应分类 | 日期边界不变时复用快照 |
| ETF份额 | 各表分别复核本地末尾3个交易日，并同步之后的增量 | 只比较小窗口；写入复用窗口已读数据，不再重复下载变化行；新表或空表首次全量 |
| 净利润断层 | 按季度头/版本定位变化；变化季度对账成员，只读变化明细；后续表现表核对主键/时间戳 | 未变季度不重读股票明细 |
| 个股机构持仓 | 专用 ownership_sync_head / ownership_change 增量，首次基线支持断点续传 | 版本不变时复用快照 |
| 高股息、高增长 | 读取当前小规模选股名单 | 当前快照比较，不扫描多年历史 |
| 创红比 | 专用只读桥校验日历及三条指数序列，导入缺失点，冲突保留原值 | 当前仍读取指数历史，远小于逐股票明细 |
| 估值标尺 | 读取日历和每日汇总；仅下载新日期、变化日期或未建立校验记录日期的成分数据 | 已确认日期不重复读300只成分明细；仍检查每日汇总 |

首次同步、完整重新同步、版本代际变化等情况仍须建立基线。同步失败保留之前成功数据。估值标尺和机构持仓均有独立断点机制。

估值标尺首次同步仍校验每天300只成分。MySQL 5.7.22及以上按日期压缩明细，每页最多50天；PE以文本传输，空值保留。旧版MySQL、MariaDB及SQLite使用每页最多1000行的主键分页。每页读完即关闭查询，再校验和检查取消，避免流式游标在超时后继续排空整表。同步仍采用只读一致性快照，全部校验通过才发布；不修改源库或跳过财务校验。实际速度取决于源库和网络，不能据此承诺固定耗时。

估值同步准备阶段分别显示连接、表结构、交易日历和每日汇总。`Valuation read start/complete/failed` 记录每批表名、格式、条数上限及耗时，重试日志的 `frames` 定位失败位置，不输出 SQL、参数或凭证。`MYSQL_2013` 表示读取连接中断，单凭错误码不能确定是网络还是数据库端原因。

估值每个完整日期校验后，保存到页面历史目录下唯一的 `.valuation-sync-pending-v1.sqlite3`，暂不对网页发布。自动重试、手动重试或进程重启后重新读取源日历/汇总，仅续用同一来源且日汇总（含更新时间）未变的完整日期，变化日期重新下载。日志 `Valuation checkpoint resumed_days=...` 表示续用天数。恢复时重验本地保存的成分与当前日汇总，全量续传仍检查源库孤立明细日期；全部完成后原子发布并删除断点。成功发布会更新代次，因此遗留断点不会让下次主动全量同步跳过检查。估值单轮时间预算为2小时，网络读取仍使用系统设置的超时；预算到达或取消也保留已校验日期。只有一个断点文件，不按重试次数堆积副本。

续传与日常增量均要求采集器修改成分时同事务更新日汇总/更新时间。手工只改明细而不更新汇总，未完成断点无法识别这种改动；应完成续传后再执行一次完整重新同步。未完成的一天始终重读，部分数据不覆盖已发布页面。

## 机构持仓为何重新读取历史

“已就绪”只表示已发布缓存可读，不表示增量游标有效。选择完整同步、本地快照/游标缺失、源库日志代次变化或版本回退时，需要重新建立基线；页面会显示原因，日志记录 `Cache ownership baseline required`。基线完成后写入游标，下一次版本相同直接跳过，版本增加只读取变更键。

`checkpoint initialized` 表示建立新断点，`baseline resume` 的 `saved_rows` 表示已保存行数。`page read` 是源库读取耗时，`page committed` 的 `write_seconds` 是本地写入耗时。进度的“已处理”含对比和重试，并非新增行数。保留断点，不删除缓存来排查慢查询。

## 为什么出现“源库未启用新版变更日志”

2026-11-11 的 1a6e09e 将行业动量、微盘新高新低从日期追加切换到结果变更日志，以识别历史补洞和修订。旧采集器没有模块日志头时，后端核对完整主键/时间戳清单，再读取变化明细；不是每次下载全部行情，但公网下仍可能慢。

本次修复行业动量的初始化遗漏：即使没有新交易日，独立版和批量版也创建日志表及模块头。此前仅在写入结果时初始化，已更新但当日无新增的脚本仍可能无法启用日志。其他结果日志日常入口已在提前返回之前初始化。

启用步骤：

1. 将最新批量脚本替换到实际使用的聚宽 Notebook；若运行独立入口，也更新对应文件。仅部署网页不会更新聚宽代码。
2. 保留 mysql_connector.py 配置，正常运行采集；日志表和模块头由脚本初始化，不清库、不手工编造版本号。
3. 网页正常同步一次建立日志基线。之后版本未变就跳过，有变化仅同步相关记录。

不要混用不维护日志的旧采集器写同一结果表，否则变化可能不推进版本。日志缺失时继续回退对账，不能仅以最大日期代替完整性检查。

## 何时需要完整重新同步

- 抱团拥挤度日期边界内的人工修改、删除或补洞。
- ETF份额末尾3个交易日之前的历史补采或修改。
- 绕过新版采集器日志，手工修改源表。
- 估值标尺只改成分而未更新每日汇总/时间戳。

在页面选择对应模块及“完整重新同步（修复历史）”。它只重新读取源库，不重算策略、不修改生产源表，也不能恢复源库已删除的数据。已接受任务不等于同步成功，以最终模块状态为准。

## 性能边界

Cache slow read 包含 SQL、网络传输及驱动读取耗时，不能只凭 Sending to client 判断本地 SQLite 写入慢。先核对首次基线、完整清单回退、网络重试及变化明细读取。

回归覆盖无新增时日志初始化、重复运行不推进版本、建立基线后不再读业务历史。测试使用模拟源，不承诺生产网络上的固定耗时。
