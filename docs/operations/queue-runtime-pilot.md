# ETF / 市场采集独立执行器（试点，默认关闭）

此阶段只分离已有持久化手动队列的 **国家队 ETF** 与 **市场热度 / 抱团拥挤度**。其他任务（包括直接启动线程的手动采集、缓存总同步、社交监控及通知）维持现有 API 生命周期。不会改变数据口径、自动时间、补采范围、MySQL 写入规则、权限或采集日志规则。

## 进程角色

配置项 `COLLECTION_RUNTIME_ROLE` 由各进程启动环境读取，重启才生效：

| 值 | 行为 |
|---|---|
| `combined`（默认） | 原有 API + 本地全部任务；无需修改已有配置。 |
| `split-api` | API 仍负责页面、授权、配置、队列提交/取消以及未分离的任务。不启动本地 ETF/市场执行线程。 |
| `queue-worker` | 独立进程，仅运行 ETF 和市场两个现有执行循环及其必要的缓存发布；不运行 HTTP 服务。 |

独立角色试点仅支持 Linux 同一主机、相同代码版本、相同 `APP_ENV_FILE` 和 **相同本地 LOG_DIR**。两进程须使用同一服务账号/权限，不支持网络文件系统、并行多主机或不同缓存命名空间。原有跨进程业务锁、队列主键、配置修订、取消标识和中断恢复仍是业务状态的权威。

默认 combined API （包括多个 Uvicorn worker）取得共享角色锁；独立执行器取得排他的角色锁。同一日志目录不能同时运行两个独立执行器、也不能在旧 combined API 仍执行任务时启动独立执行器。启动冲突会明确失败。不应手工删除锁文件。

## 本地/预发布试点

先在隔离日志目录和数据库环境验证。不要在正在运行的生产服务上直接试验：

1. 等待已有采集终态，正常停止现有 combined API，确认角色锁已释放。
2. 使用相同应用配置与代码版本，从 backend 目录启动独立进程（由本地预发布进程管理器负责监督）：
   ```sh
   COLLECTION_RUNTIME_ROLE=queue-worker python -m app.queue_worker
   ```
3. 用同一配置与日志目录启动 API：
   ```sh
   COLLECTION_RUNTIME_ROLE=split-api python run.py --host 127.0.0.1 --port 8000 --workers 2
   ```
4. 验证 `GET /api/v1/health` 保持原有存活语义；`GET /api/v1/readiness` 应在执行器租约和两条调度线程新鲜心跳均可核验时返回 HTTP 200，否则 503。它只检查本地生命周期，不主动连接数据库或交易所，也不证明数据已更新。业务完整性仍查看各模块状态和采集记录。
5. 验证一次授权的手动队列提交、同 ID 重放和取消。split API 不启动本地采集线程；新任务通过原持久队列交给独立进程，唤醒文件由心跳循环读取（约两秒）。唤醒失败不会否认已经写入的队列，原30/60秒调度轮询仍继续。

执行器缺失、心跳未知/过期或正在排空时，新手动队列请求返回不可用（HTTP 503）；已有请求允许查询/重放与取消，不删除。已有排队任务优先保留原有忙碌错误。如果请求恰好在排空通知前提交，它仍然是持久化的真实排队请求，可由下一次正常执行器启动恢复；不会报告为已完成。

## 排空与恢复

对独立执行器正常发送 SIGTERM/SIGINT，监督线程会关闭新 tick 的进程内准入门并发布 draining 心跳；已进入的 tick 按原规则完成，最多等待20秒。随后对尚未退出的任务请求原有协作式停止，并共享最多10秒 join 预算。已排队但未领取的任务不在关闭过程中启动。停机前已经进入的 tick 即使稍后才领取，也属于本轮已准入工作，不会被错误标为未执行。

若网络/数据库调用在预算内仍不返回，进程报告未完全停止并以非零状态退出，由原持久队列和事务恢复逻辑处理。未知 MySQL 提交不伪称回滚/成功；该方案不是强制中断驱动 I/O，也不替代原业务重试规则。角色锁至少持有到仍活着的执行线程结束或进程退出；不会在同一活跃进程中提前允许另一角色。

原 combined 模式的停服行为保持不变。本试点未解决其他模块的串行停止预算，也未调整 production systemd 或 MySQL 超时配置。

## 发布兼容性与回退

**现有自动部署仅编排 API 服务，未编排本独立执行器。请保持生产角色 combined；不得开启生产 split-api，直到后续部署阶段同时管理两个进程的版本校验、健康检查和回滚。** 现在发布此代码不改变默认启动行为或原 `/health` 发布门槛。

预发布回退：正常停止 split API；停止并确认独立执行器进程已退出；用原配置重新启动 combined API。无需迁移数据库、删除心跳、清理队列或修改工作数据。遗留心跳不能在无独立角色锁、协议版本不匹配时当作可用。心跳协议 v2 会比较实际 backend 源码和依赖锁文件的启动指纹；不匹配、缺失、旧协议、退出进程或进程启动代次不符会拒绝新任务且 readiness 返回 503。此检查不证明完整 Git SHA、前端版本或实际安装依赖一致，仍须由发布管理保证。已有业务中断由原持久账本恢复，禁止为绕过冲突手工删除角色锁。

## 自动发布保护与正式切换的验收条件

当前 API-only 发布脚本新增双重保护：准备前及实际停止 API 前，根据 systemd 的工作环境和同一外部 dotenv 配置解析角色；只允许有效角色为 `combined`，并确认约定的 `showallopts-queue-worker.service` 未处于活动或过渡状态。准备过程中改变 systemd 环境也会拒绝切换。缺少配置检查能力、角色非法或独立服务状态不可确认时失败关闭；不进入代码、虚拟环境或前端切换事务。保护不需要新增 sudo 权限。它不会安装、启动或停止独立执行器，不支持任意命名的手工进程；预发布试点不能与这个发布脚本同时运行。运维人员不可在发布锁持有期间修改服务单元或配置。

正式 split 模式需要一个**明确协调两服务的发布事务**，在隔离 Linux 环境/实际 systemd 预发布通过以下验收前保持 combined：

1. **固定拓扑**：root 管理固定名称 `showallopts-api.service` / `showallopts-queue-worker.service`。后者使用相同服务用户、工作目录、只读代码/依赖路径、私有 APP_ENV_FILE 和 LOG_DIR，明确 `COLLECTION_RUNTIME_ROLE=queue-worker`，`ExecStart=…/backend/.venv/bin/python -m app.queue_worker`，不监听端口；API 角色由自己的 systemd 环境覆盖为 `split-api`。固定最小权限的 root helper 只允许指定两服务的状态/启动/停止操作（验证服务账号、工作目录和 root-owned unit；不接受任意命令/参数）。需独立的人为安装或审批，不通过仓库可写脚本自行扩权。
2. **同一版本**：构建一次、检查一次、两个服务从同一已验证的完整 Git SHA/发布目录和同一锁定虚拟环境启动。由受信任的启动器绑定完整发布 SHA 与实际不可变代码路径（不能只依赖手工环境变量、PID 或心跳协议版本）；两个进程启动时报告绑定的 release ID，监督进程核验 worker 实际 cgroup/PID/启动代次与该发布，API readiness 需要匹配同一 release ID 的新鲜独立租约。公开 health 不暴露配置、绝对路径或凭据。当前已实现角色租约、协议、新鲜度、Linux 本地进程启动代次及后端启动指纹检查（实际 backend app 下的 Python/JSON 文件、run.py、依赖锁文件和 Python 版本；按内容计算，不信任手工 release 标签）；不同指纹时 readiness 503 且不接受新请求。当前检查不替代完整 Git SHA、不可变部署路径和已安装 venv 的验收。
3. **停止与切换**：保留原完整发布记录、静态文件及环境，先关闭 API 新任务入口/停 API，向独立执行器发送 SIGTERM 并等待原队列排空预算与进程退出（独立执行器 systemd TimeoutStopSec 必须大于其 20+10 秒内部预算并留出退出余量，例如预发布验证 60 秒；其他 API 任务另测，不从此推导所有模块可在 30 秒停完）。确认两服务均已停止、旧角色锁已释放后才换代码/环境。不删除队列、业务锁、心跳或配置，不擅自恢复未知数据库提交。未确认停服则不换版本。
4. **启动与验证**：启动新 worker，核实其新启动代次、同版本、两条调度线程健康与独占租约；再启动 API，核实本地 HTTP 监听归属及同版本 readiness 200；最后发布静态资产并核实站点字节及再次核验两服务。真实业务采集是否成功仍看原记录；发布检查不得主动制造真实数据更新或第三方通知。
5. **失败回退**：记录两服务原始状态、完整 SHA、历史发布环境及静态备份。在任一步失败时先停止并验证两个新进程均已退出，再恢复上一完整发布与原角色拓扑，worker 先于 split API 启动；combined 只启动 API。重复验证上一步的健康和版本门槛。回退不删除或恢复业务数据库/队列；若停服/版本一致性无法证明，保持失败状态并要求人工核查，而非强制覆盖活跃 release。
6. **发布测试矩阵**：combined 平滑升级、split 两服务同版本升级、旧进程仍活跃/旧心跳/混合版本、worker 启动失败或后续退出、API 启动失败、队列 drain 超时、静态发布失败、回滚启动失败及部署中断。检查相同 manual run ID 不重复执行、待执行项未丢、取消有效、历史结果未改、没有新增未授权权限。自动部署成功必须依赖两服务门槛及站点验证，而不是只看到 API HTTP 200。

现阶段实现生产默认不变的 API-only 保护、试点生命周期及后端启动指纹握手，并在独立子进程+模拟采集器验证不同版本拒绝及同版重启恢复。完整双服务发布、完整 Git SHA 与不可变 release/venv 绑定、root helper/单元安装、实际 systemd 集成测试及正式 cutover 是后续显式运维工作，未声称已经完成或启用。
